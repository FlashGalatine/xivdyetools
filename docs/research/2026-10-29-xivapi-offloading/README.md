# XIVAPI responsibility review

Date: 2026-10-29. Status: research complete; proposed implementation requires a separate decision.
Addresses [issue #322](https://github.com/FlashGalatine/xivdyetools/issues/322).
Code baseline: `13c386e5` on `main`; held adoption/release PRs are not integrated here.

The [2026-10-20 investigation](../../audits/2026-10-20-xivapi-offloading/README.md) already completed the original research, and its [implementation handoff](../../audits/2026-10-20-xivapi-offloading/IMPLEMENTATION.md) records the subsequently approved Stain audit. Issue #322 remained open despite that work. This dated refresh reconciles the issue with current main, checks fresh public samples and identifies the next optional maintenance change. The historical reports remain unchanged.

## Recommendation

Use XIVAPI for **pinned maintenance inputs** and retain the existing **cached API-worker equipment and icon integration**. Keep the dye database and color work local. A runtime migration of dye names or colors would introduce network failure into tools that currently work without it, while still needing regional sources for Korean and Chinese.

The bounded first change recommended for separate implementation is **capture, validate and replay the canonical schema pin in the acquisition generator**, alongside its existing game-version pin. This closes a reproducibility gap without replacing curated acquisition rules or changing the runtime response. The acceptance criteria below deliberately precede any implementation.

## Operational comparison

| Approach | Fit and cost | Failure / privacy / compatibility behavior |
|---|---|---|
| Pinned maintenance refresh | Preferred for dye metadata, regional tables and acquisition. Network work happens once per reviewed update; checked-in outputs cost no upstream calls during use. | Record canonical game version, full schema revision, source commits/hashes and capture date. Bounded fetches, response validation and offline replay must fail without overwriting adopted data. Stale-but-known bundled data remains available. |
| Browser requests directly to XIVAPI | Technically possible: sample JSON responses return `Access-Control-Allow-Origin: *`. Adds a request per uncached browser need and another failure path. | Current SPA CSP and privacy disclosures would need review for a new origin. Requests disclose visitor network metadata and requested identifiers upstream. Abort navigation requests, cap time/body/rows and retain local fallback; CORS alone is not a reason to migrate. |
| Optional runtime requests through API-worker | Already used for equipment/icons. Shared caches amortize repeated lookups; regional supplementation and normalization stay centralized. Cold misses add upstream latency and Worker work. | Keep same-origin/first-party browser delivery. Do not forward `.chara` names or full files upstream. Budget misses, cache negative answers separately from outages, bound retries/coalescing and keep cancellations from poisoning other waiters. Preserve existing public response shapes. |

### Existing controls and remaining limits

- The API-worker discovers canonical version/schema context (ten-minute success memo, one-minute failure memo) and namespaces row caches by upstream origin, canonical pins and shape version. Row freshness is seven days with one further day of stale retention. It already limits pending lookups to 256 keys and bypasses unsafe caching/coalescing when context is unresolved. See [`cache.ts`](../../../apps/api-worker/src/chara/cache.ts), [`lookup-loader.ts`](../../../apps/api-worker/src/chara/lookup-loader.ts) and the client.
- Icon identity includes origin, canonical game version and icon ID, with seven-day freshness, thirty-day retention and PNG/one-MiB checks. These are existing controls, not proposed new caching work.
- Web resolution combines caller cancellation with its timeout; Discord has a twelve-second API call timeout. The API upstream client has a ten-second timeout; caller cancellation is not directly propagated into that upstream signal. Preserving shared work while bounding its owner needs deliberate tests, rather than blindly forwarding one waiter's abort signal.
- The older Python name fetcher has no game/schema pin, while the Stain audit already captures both and supports offline replay. Acquisition generation captures game version but does not capture/send a schema pin. Those maintenance gaps should not be confused with missing runtime pinning.
- No numeric public service quota or SLA was established by this review. Treat upstream as best effort, respect 429/Retry-After and caching guidance, and agree production expectations with its maintainers. These samples do not measure sustained capacity, availability or browser-to-Worker production latency.
- Single sample elapsed times ranged from 318 ms to 16,608 ms for successful metadata requests. This is evidence for a bounded timeout and fallback, not a benchmark or claim about normal response time. One slower valid sample would exceed the application's existing ten-second upstream deadline.

## Identity, localization and rights requirements

Canonical dye identity remains `stainID`. Compatibility `Dye.itemID` and locale keys still use `legacyItemID` where available; consolidated **market item** IDs have their own mapping in [`consolidated-ids.ts`](../../../packages/core/src/config/consolidated-ids.ts). The sampled Stain rows both link to Item 52254, illustrating why a linked Item is not a unique per-color identity. Preserve historical links, share URLs, collections and migrations; do not replace identifiers by row order or localized text.

Keep game-data strings separate from authored UI translations. The global client has four locales; the Chinese and Korean editions have separate schedules. Preserve the six supported UI locales even when an upstream locale is unavailable. No unsupported source is filled by inference.

Source availability is not a grant of redistribution rights. Preserve existing Square Enix notices and the relevant source/project licenses and attribution when generating data or serving assets; an open-source API implementation's license does not itself license the game's assets. Reassess attribution for any newly added source. This review makes no new rights determination or license change.

## First-change acceptance criteria — acquisition schema pinning

1. Capture the first successful canonical game version **and** canonical schema specifier; send both on every subsequent sheet/search request. Explicit replay pins must never silently resolve to `latest`.
2. Reject missing/malformed/mismatched pins before publishing outputs, including a mid-run schema or version change. Save both pins in generation metadata and cache identity. Keep any mutable discovery separate from immutable replay.
3. Replay the existing committed acquisition output from cached, pinned inputs with zero line changes. The current table's recorded game pin must not be refreshed as a side effect. Preserve source selection, special-case generator rules and deliberately blank lines.
4. Exercise first-response capture, paginated/batched requests, explicit replay, malformed/mismatched pins, incomplete data, 429/503 and transport failure. No partial output adoption on failure.
5. Review the generator's timeout/body/retry limits explicitly before implementation; separate their hardening from any data/content change. Document the invocation and provenance contract in the maintainer guide.

Alternative follow-up: adapt or retire the older Item-based name fetcher around the **already existing** Stain audit snapshots. It is not a request to create a second Stain importer. Runtime dye outsourcing is not recommended.
