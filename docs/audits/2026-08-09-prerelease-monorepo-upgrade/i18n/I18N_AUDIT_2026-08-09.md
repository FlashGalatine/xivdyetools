### ⚠️ `core` locales are build artifacts — fix the generator, not the file

```jsonc
// packages/core/package.json:24
"build": "npm run build:version && npm run build:locales && tsc … && npm run copy:locales",
"build:locales": "tsx scripts/build-locales.ts",
```

The root `CLAUDE.md` states it directly:

> `build:locales` regenerates from `dyenames.csv` / `localize.yaml`, so hand-edits to the
> generated locale JSON are **overwritten** — fold corrections into the source files instead.

**Any correction to a `core` locale must land in `packages/core/dyenames.csv` or
`localize.yaml`.** Editing `packages/core/src/data/locales/*.json` directly is reverted by the
next build. This is why `core` shows perfect 263/263 parity across all six languages — it is
mechanically generated and structurally cannot drift.

`bot-logic` and `web-app` locales *are* hand-maintained and are the correct edit targets for
their own trees.

## The 24-key "missing" result is a NON-FINDING — verified, not assumed

The raw parity scan reported 24–25 missing keys per locale. **Every one is a
`preset.*.tags[N]` array element, and none is a defect.** This was traced before being filed,
because reporting it as a gap would have generated 122 spurious remediation items.

**What is actually happening:** English authors 4 tags per curated preset; the translations
author 2–3. The tag lists are *authored per language*, not mechanically translated.

```
en  season-winter  -> ['winter', 'snow', 'frost', 'cold']      (4)
de  season-winter  -> ['winter', 'schnee']                     (2)
ja  season-winter  -> ['冬', '雪']                              (2)
zh  season-winter  -> ['冬', '雪']                              (2)

en  gc-flames      -> ['immortal flames', 'uldah', 'desert', 'fire']  (4)
de  gc-flames      -> ['unsterbliche', 'ul'dah', 'wüste']             (3)
ja  gc-flames      -> ['不滅隊', 'ウルダハ', '砂漠']                    (3)
```

**Three pieces of evidence that this is deliberate:**

1. **It is perfectly systematic.** All five locales drop the *same* indices across all 15
   presets. Accidental omission does not produce that pattern; a translator writing 2–3
   meaningful tags per language does.
2. **The design record says these were authored and confirmed**, not machine-translated:
   > the curated 15, whose ×6 names/descriptions/tags were drafted + confirmed 2026-08-07
   > (`String Pass — Curated Presets.dc.html`)
3. **The consuming code handles variable length safely** — no fixed indexing anywhere:
   ```ts
   // preset-tool.ts:562   — search
   p.tags.some((t) => t.toLowerCase().includes(q))
   // preset-detail.ts:958 — render
   ${this.preset.tags.map((tag) => html`<span class="tag">${tag}</span>`)}
   ```
   `.some()` and `.map()` over a 2-element array are correct. There is no `tags[3]` read
   anywhere that could throw or render `undefined`.

**No action required.** Recorded here so the next audit does not re-file it.

### One genuine consequence worth knowing (not a defect)

Because tags drive the preset search filter, **search coverage differs per language**. A German
user searching *"frost"* will not surface Winter (German tags are `['winter','schnee']`), while
an English user will. This is the natural consequence of authored-per-locale tags and is
arguably correct — German users search in German. Flagging it only so it is a known property
rather than a future bug report.

## Untranslated-looking values — all 62 verified legitimate

The scan flags a target value identical to its English source. All 62 were reviewed
individually; **none is a translation gap.** They fall into four legitimate classes:

| Class | Examples | Why identical is correct |
|-------|----------|--------------------------|
| **Brand / proper nouns** | `about.title` "XIV Dye Tools Bot", `common.footer`, `firstRun.title` "XIV Dye Tools 5.0" | Product names do not localise |
| **Standards identifiers** | `wcagAA` "WCAG AA", `wcagAAA` | The design record is explicit: *"Identifiers are not quantities — criterion numbers, item IDs, stain IDs never localise"* |
| **Method tags & units** | `budget.colPerDe` "GIL / ΔE", `comparison.mCie76Short` "ΔE76 · CIE 1976", `mOklabShort` "ΔEOK · OKLab" | The record fixes these verbatim ×6: *"Tags: `ΔE2000` `ΔEOK` `ΔE76` `REDMEAN` `RGB DIST` `DISTINGUISH %` `RATIO`"* |
| **True cognates** | fr `config.via` "via {provider}", fr `preset.voteCount` "{count} vote", de `swatch.palTattoo` "Tattoo / Limbal" | "via", "vote", "Tattoo" are the correct French/German words |
| **Command literals** | `manual.dyeRandom.name` `` `/dye random [unique_categories]` `` | The record: *"A stored choice value (command, topic, `square`, Spectrum item name) stays verbatim ×6"* |

**One borderline case worth a translator's eye, not a fix:**

- `de` `budget.maxDistance` = `"Max Delta-E"` — "Max" is idiomatic German, and "Delta-E" is a
  unit identifier. Defensible as-is; flag only if the German reviewer prefers *"Max. Delta-E"*
  (with the abbreviation period the record calls for elsewhere: *"DE/FR abbreviation periods
  part of the key"*).

## Recommendations

1. **Re-run `discord-worker`'s subsetter** (FONT-001). This is the only user-visible i18n defect
   and it affects three of six languages.
2. **Extract the 4 hardcoded strings** in `preset-detail.ts` (HC-001…004). Three of them already
   have locale keys authored in all six languages — the keys exist and simply are not called.
3. **Remember the generator rule** for any `core` locale correction: edit `dyenames.csv` /
   `localize.yaml`, never the JSON.
4. **Add an i18n parity check to CI.** The analysis in `evidence/i18n-parity.txt` is ~120 lines
   of Python. Wired as a non-blocking CI report, it would catch a duplicate key or a dropped
   `{count}` the day it lands, rather than at audit time. Configure it to treat `preset.*.tags`
   as variable-length so it does not re-report the non-finding above.
5. **Add the font-coverage check to the same CI step** — it is the check that would have caught
   FONT-001, and stale subsets are the failure mode most likely to recur, since every locale
   string change invalidates them.
