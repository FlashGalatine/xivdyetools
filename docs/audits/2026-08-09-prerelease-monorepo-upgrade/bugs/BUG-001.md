# [BUG-001]: Registered `/preset` schema still offers the retired `community` category

## Severity
HIGH

## Type
Logic error / contract drift between a registered external schema and its backing type

## Location
- File: [apps/discord-worker/src/commands/schemas.ts](../../../../apps/discord-worker/src/commands/schemas.ts)
- Lines: **918, 964, 997** — three separate subcommand option blocks
- Contradicted by: [packages/types/src/preset/core.ts:12-17](../../../../packages/types/src/preset/core.ts)

## Deploy Unit
`discord-worker` — and critically, this is a **registered command schema**, so the fix requires
a `register-commands` run against Discord, not just a `wrangler deploy`.

## Description

The 5.0 design record is unambiguous:

> **`community` category dropped everywhere**: enum value, `ICON_CATEGORY_COMMUNITY`,
> `CATEGORY_ICONS` key, submission/edit forms, `preset-submission-service.ts` (nine declaration
> sites tabled in the register).
> — `XIVDyeTools-redesign-5.0/CLAUDE.md` § Community Presets

The type change landed. `PresetCategory` is now five members:

```ts
// packages/types/src/preset/core.ts:12
export type PresetCategory =
  | 'jobs'
  | 'grand-companies'
  | 'seasons'
  | 'events'
  | 'aesthetics';
```

`web-app` was updated too — `hybrid-preset-service.ts:216` even carries the comment
*"5.0: the 'community' category value is dropped everywhere"*.

**The Discord command schema was not.** Three subcommands still present `🌐 Community` as a
selectable category choice, sending the string `community` to a system that no longer has that
category.

## Reproduction Scenario

1. Register commands with the current schema (`pnpm --filter xivdyetools-discord-worker run
   register-commands`).
2. In Discord, invoke the `/preset` subcommand carrying the `category` option.
3. Discord's native autocomplete offers **🌐 Community** — it is a registered choice, so the
   client presents it as a first-class, valid option.
4. Select it. The bot forwards `category=community` to `presets-api`.
5. The category no longer exists in `PresetCategory`. The request either returns an empty result
   set or is rejected — either way the user picked a menu item Discord told them was valid and
   got nothing back, with no explanation.

This is the worst kind of failure for a released bot: **the platform itself vouches for the
broken input**. The user cannot tell it is a bug rather than an empty category.

## Evidence

All three sites are byte-identical, appended to the same five-member list:

```ts
// apps/discord-worker/src/commands/schemas.ts:912-919 (repeated at 958-965 and 991-998)
            choices: [
              { name: '⚔️ FFXIV Jobs',      value: 'jobs' },
              { name: '🏛️ Grand Companies', value: 'grand-companies' },
              { name: '🍂 Seasons',         value: 'seasons' },
              { name: '🎉 FFXIV Events',    value: 'events' },
              { name: '🎨 Aesthetics',      value: 'aesthetics' },
              { name: '🌐 Community',       value: 'community' },   // ← retired in 5.0
            ],
```

```
$ grep -n "Community', value: 'community'" apps/discord-worker/src/commands/schemas.ts
918:              { name: '🌐 Community', value: 'community' },
964:              { name: '🌐 Community', value: 'community' },
997:              { name: '🌐 Community', value: 'community' },
```

**Why the type system did not catch it:** these choice arrays are plain object literals typed
by the Discord application-command shape (`{ name: string; value: string }`). Nothing ties
`value` back to `PresetCategory`, so removing the union member produced no compile error. This
is precisely why 24/24 type-check tasks pass with the bug present.

## Why It's Hidden

- **No type linkage.** The schema's `value` is a bare `string`; the union narrowing that would
  have flagged it does not reach here.
- **No test asserts choice/enum parity.** `about.test.ts` asserts *command roster* parity
  against `registry.ts`, but nothing asserts *option choice* parity against `PresetCategory`.
- **Grep noise masks it.** Searching `'community'` returns many legitimate hits that are
  unrelated domains — `registry.ts:19,51` uses `community` as a **command grouping** for
  `/about`, and `preset-tool.ts` uses it as a **UI tab name**. Both are correct and must stay.
  The three schema hits are easy to dismiss as more of the same.
- **The schema only bites after `register-commands`.** Local dev and the test suite never
  exercise the registered Discord surface.

## Suggested Fix

Delete the three lines:

```ts
            choices: [
              { name: '⚔️ FFXIV Jobs',      value: 'jobs' },
              { name: '🏛️ Grand Companies', value: 'grand-companies' },
              { name: '🍂 Seasons',         value: 'seasons' },
              { name: '🎉 FFXIV Events',    value: 'events' },
              { name: '🎨 Aesthetics',      value: 'aesthetics' },
            ],
```

Then **close the class, not just the instance** — this is the defect that lets it recur. Derive
the choices from the type instead of hand-listing them:

```ts
import type { PresetCategory } from '@xivdyetools/types';

const PRESET_CATEGORY_CHOICES: ReadonlyArray<{ name: string; value: PresetCategory }> = [
  { name: '⚔️ FFXIV Jobs',      value: 'jobs' },
  { name: '🏛️ Grand Companies', value: 'grand-companies' },
  { name: '🍂 Seasons',         value: 'seasons' },
  { name: '🎉 FFXIV Events',    value: 'events' },
  { name: '🎨 Aesthetics',      value: 'aesthetics' },
];
```

Typing `value` as `PresetCategory` makes the next dropped member a **compile error at all three
sites at once**, and referencing one shared constant removes the triplication entirely.

Add a parity test alongside the existing `about.test.ts` roster assertion:

```ts
it('offers exactly the live PresetCategory members', () => {
  expect(PRESET_CATEGORY_CHOICES.map(c => c.value).sort())
    .toEqual(['aesthetics', 'events', 'grand-companies', 'jobs', 'seasons']);
});
```

### Deployment note

Because this changes a **registered** schema, shipping it requires:

1. `wrangler deploy` (or `deploy:production`) for the handler, then
2. `pnpm --filter xivdyetools-discord-worker run register-commands` to push the new choice list
   to Discord.

Step 2 is user-run per the project's deploy process. Until it runs, the stale choice stays
visible in Discord clients regardless of what the Worker code says — so **the register step is
the actual fix**, and the code change alone does not close this finding.
