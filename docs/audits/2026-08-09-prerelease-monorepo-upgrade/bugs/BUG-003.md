# [BUG-003]: `parseInt` on a Discord snowflake loses precision, selecting the wrong default avatar

## Severity
LOW

## Type
Edge case / numeric precision (silent wrong-but-plausible result)

## Location
- File: [apps/web-app/src/components/v4/config-sidebar.ts](../../../../apps/web-app/src/components/v4/config-sidebar.ts)
- Line: 1565

## Deploy Unit
`web-app`

## Description

Discord's default-avatar URL is selected by taking a user's ID modulo 5. The code does this
with `parseInt`:

```ts
// apps/web-app/src/components/v4/config-sidebar.ts:1565
`https://cdn.discordapp.com/embed/avatars/${parseInt(user.id || '0') % 5}.png`;
```

Discord user IDs are **snowflakes** — 64-bit integers rendered as decimal strings, typically
18–19 digits. JavaScript's `Number` is an IEEE-754 double with 53 bits of integer precision
(`Number.MAX_SAFE_INTEGER` = 9,007,199,254,740,991 — 16 digits). Every modern Discord ID
therefore **exceeds safe integer range**, and `parseInt` silently rounds to the nearest
representable double before the `% 5` is applied.

The result is a stable but arbitrary avatar index that does not match the one Discord itself
computes.

## Reproduction Scenario

```js
const id = '1234567890123456789';        // a realistic 19-digit snowflake
parseInt(id)                             // 1234567890123456800   ← rounded, ≠ input
parseInt(id) % 5                         // 0
BigInt(id) % 5n                          // 4n                    ← the correct answer
```

A user whose Discord profile shows the *red* default avatar sees the *blurple* one in the web
app's config sidebar. It is cosmetic and consistent per user, so it reads as a design
difference rather than a bug.

Two secondary notes on the same line:

- **Missing radix.** `parseInt` without a radix is a lint-flagged pattern generally; here the
  input is always decimal digits so it is benign, but it should still be explicit.
- **`|| '0'` masks a real absence.** An empty/undefined `user.id` silently becomes avatar 0
  rather than rendering a genuine no-user state.

## Evidence

This is the only unradixed `parseInt` in the codebase operating on real data:

```
$ grep -rn "parseInt([^,)]*)" --include="*.ts" packages/*/src apps/*/src | grep -v ", *[0-9]"
apps/discord-worker/src/handlers/commands/budget.ts:156:  // …comment only, explaining a guarded parseInt…
apps/web-app/src/components/v4/config-sidebar.ts:1565:  …${parseInt(user.id || '0') % 5}.png
```

`budget.ts:156` is a comment documenting an *already-guarded* numeric parse
(*"entirely numeric — parseInt('255 Brown') would otherwise parse as 255"*), so it is not a
defect — evidence that this class was considered elsewhere and simply missed here.

## Why It's Hidden

- **The output is always valid.** `% 5` yields 0–4 regardless, so the URL always resolves to a
  real Discord asset. There is no 404, no error, no console warning.
- **It is deterministic per user.** The same user always gets the same wrong avatar, so it never
  looks flaky.
- **It only affects users with no custom avatar** — a minority, since most Discord accounts
  upload one.
- **Tests cannot catch it without a snowflake fixture.** A short numeric test ID
  (`'123456'`) round-trips through `parseInt` perfectly and passes.

## Suggested Fix

Use `BigInt`, which is exact for 64-bit values and is supported in every target the app
already requires:

```ts
/**
 * Discord default-avatar index. IDs are 64-bit snowflakes that exceed
 * Number.MAX_SAFE_INTEGER, so Number/parseInt rounds them and the modulo
 * lands on the wrong avatar. BigInt is exact.
 */
function defaultAvatarIndex(id: string | undefined): number | null {
  if (!id || !/^\d+$/.test(id)) return null;   // absent/invalid ≠ avatar 0
  return Number(BigInt(id) % 5n);
}
```

then at the call site:

```ts
const idx = defaultAvatarIndex(user.id);
const avatarUrl = idx === null
  ? /* genuine no-user / unknown state */
  : `https://cdn.discordapp.com/embed/avatars/${idx}.png`;
```

Returning `null` rather than defaulting to `0` also fixes the `|| '0'` masking — an absent user
is a state worth rendering deliberately, not silently as "avatar 0".

Add a regression test with a real-length snowflake:

```ts
it('picks the avatar Discord picks, for IDs past MAX_SAFE_INTEGER', () => {
  expect(defaultAvatarIndex('1234567890123456789')).toBe(4);   // not 0
});
```

> **Note on newer Discord accounts:** Discord migrated non-migrated (legacy, discriminator-bearing)
> accounts to `discriminator % 5` and migrated accounts to `(id >> 22) % 6`. If the sidebar is
> meant to mirror Discord exactly for *all* accounts, confirm which rule applies to the users
> this component renders before finalising the formula — the precision fix above is necessary
> either way, since both rules need the exact integer.
