# [BUG-002]: web-app still applies the retired Habibi proportional serif to every numeric column

## Severity
MEDIUM

## Type
Design-conformance defect with a live rendering consequence

## Location
- File: [apps/web-app/src/styles/globals.css](../../../../apps/web-app/src/styles/globals.css)
- Lines: 8–14 (`@font-face`), 25–29 (the `!important` application)
- Asset: `apps/web-app/public/fonts/habibi-v22-latin_latin-ext-regular.woff2` (14.2 KiB, served)
- Consumers: 10 call sites across `extractor-tool.ts`, `gradient-tool.ts`, `mixer-tool.ts`,
  `swatch-tool.ts`

## Deploy Unit
`web-app`

## Description

Habibi was retired in 5.0 for a specific, measured reason — it is a **proportional display
serif**, so digits have unequal advance widths and numeric columns do not align. The record
states it as a defect to fix:

> **Generator defects to fix regardless of frames:** `FONTS.mono = 'Habibi'` (not monospace) →
> Fragment Mono
> — `XIVDyeTools-redesign-5.0/CLAUDE.md` § discord-worker 5.0

`packages/svg` carries the completed correction in its own comment:

```ts
// packages/svg/src/base.ts:303
//   (the previous 'Habibi' was a proportional serif — numbers never aligned)
```

Both graphics Workers moved to `FragmentMono-Regular.ttf`, and `discord-worker`'s
`test-font-rendering.ts` even lists `Habibi-Regular.ttf` in a `RETIRED_FONTS` array.

**The web app never moved.** `globals.css` still declares the face and force-applies it to the
exact elements the decision was about — hex codes, prices, ΔE values, contrast ratios:

```css
/* apps/web-app/src/styles/globals.css:7-14 */
/* Habibi - Used for numerical values (HEX codes, prices, distances, etc.) */
@font-face {
  font-family: 'Habibi';
  font-style: normal;
  font-weight: 400;
  font-display: swap;
  src: url('/fonts/habibi-v22-latin_latin-ext-regular.woff2') format('woff2');
}

/* :25-29 */
.number,
.font-numeric {
  font-family: 'Habibi', serif !important;
  letter-spacing: 0.02em;
}
```

## Reproduction Scenario

1. Open the web app, go to the Gradient or Swatch tool.
2. Generate a result set — any view with a stacked column of ΔE values or hex codes.
3. The digits render in Habibi, a proportional serif: `1` is markedly narrower than `0`, so
   values in a vertical column do not line up at the decimal point.
4. The same data rendered by the Discord bot or the OG card — through `packages/svg`, in
   Fragment Mono — aligns correctly.

The result is that **the same measurement looks different, and worse, on the web surface than
on the bot surface**, which is precisely the cross-surface inconsistency the 5.0 vocabulary
work set out to eliminate.

## Why It's Hidden

- **It renders.** There is no error, no console warning, no failed test — just slightly worse
  typography that reads as a design choice unless you know the decision.
- **The `!important` hides it from overrides.** Any 5.0 component trying to set a monospace face
  on a `.number` element loses silently.
- **Two-hop import.** `main.ts` importing `tailwind.css` rather than `globals.css` makes the
  file look unreferenced on a first grep — the rule survives because nobody traced the
  `@import`.
- **The header comment misdirects.** `globals.css` line 1 reads *"XIV Dye Tools v2.0.0"*, so the
  file reads as legacy that is presumed unused.

## Suggested Fix

Point the numeric class at Fragment Mono, matching every other surface. Self-host it — the file
already exists in the repo at `apps/discord-worker/src/fonts/FragmentMono-Regular.ttf` and is
122 KiB:

```css
/* Fragment Mono — the suite numeric face (5.0). Replaces Habibi, a proportional
   serif whose digits had unequal advance widths, so numeric columns never aligned. */
@font-face {
  font-family: 'Fragment Mono';
  font-style: normal;
  font-weight: 400;
  font-display: swap;
  src: url('/fonts/FragmentMono-Regular.woff2') format('woff2');
}

.number,
.font-numeric {
  font-family: 'Fragment Mono', ui-monospace, 'Cascadia Mono', Consolas, monospace;
  font-variant-numeric: tabular-nums;
  letter-spacing: 0.02em;
}
```

Three notes on the replacement:

1. **Drop the `!important`.** It exists only to beat Tailwind utilities; scope the rule
   properly instead so 5.0 components can still override where a design calls for it.
2. **Add `font-variant-numeric: tabular-nums`.** This is the property that actually guarantees
   column alignment, and it also fixes the fallback path — if Fragment Mono fails to load, the
   system monospace still aligns.
3. **Mind the CJK rule.** The design record notes Fragment Mono has no CJK coverage
   (*"mono labels fall back to the body sans at 0.04em (no CJK in Fragment Mono…)"*). The
   fallback chain above degrades to the system monospace, which is acceptable for the web
   surface where digits — not CJK — are what `.number` wraps. Verify against a ja/ko/zh session
   that no `.number` element wraps CJK text.

Convert the TTF to woff2 for the web (`fonttools`'s `ttx`/`woff2_compress`, or
`pyftsubset --flavor=woff2`), place it in `apps/web-app/public/fonts/`, and delete
`habibi-v22-latin_latin-ext-regular.woff2` in the same commit (tracked as `DEAD-004`).

Also update the two stale comments while in the file — line 1's `v2.0.0` header and the
`.number` doc block describing Habibi (`REFACTOR-005`).
