### INF-01 — CI's Cloudflare deploy credential is repository-scoped, so the `production` environment gate constrains the workflows, not the credential

- **Severity:** LOW · **Exposure:** LOCAL (requires push access to this repository; forks get no secrets) · **Rotation:** none required (no leak); rotate `CLOUDFLARE_API_TOKEN` when it is moved (natural point).
- **Where (CONFIRMED):** the three beta workflows deploy with `secrets.CLOUDFLARE_API_TOKEN` from jobs that reference **no** environment and run on **any** non-main branch push:
  - `.github/workflows/deploy-og-worker-beta.yml:18-32` (`push: branches-ignore: [main, master, dependabot/**]` + `workflow_dispatch`), `:46-47` (job, no `environment:`), `:74-82`:
    ```yaml
    uses: cloudflare/wrangler-action@ebbaa1584979971c8614a24965b4405ff95890e0 # v4
    with:
      apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
      accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
      workingDirectory: apps/og-worker
      command: deploy
    ```
  - same shape: `deploy-discord-worker-beta.yml:13-29, 43-53, 76-83`; `deploy-web-app-beta.yml:19-32, 46-47, 89-94`.
  - The nine production jobs use the **same secret name** under `environment: production` (e.g. `deploy-og-worker.yml:33-34, 55-62`).
- **Why it matters:** a job with no `environment:` can only read repository/organisation secrets, so `CLOUDFLARE_API_TOKEN` exists at repository scope and is available to every workflow run of every non-fork push. GitHub runs the **pushed ref's** copy of a workflow file, so a branch whose `deploy-og-worker-beta.yml` says `command: deploy --env production` (or a brand-new workflow with `on: push`) deploys production from an unmerged branch without touching `main` or the `production` environment. Cloudflare API tokens cannot be scoped to a Worker name, so the token that deploys `xivdyetools-og-worker-dev` deploys `xivdyetools-og-worker`. The 2026-08-21 FINDING-009 statement holds for `workflow_dispatch` of the *existing* workflows (deployment branches = `main`, `POST_MERGE_CHECKLIST.md:62-63`); it does not hold for the credential.
- **Trigger:** collaborator or compromised maintainer account/machine pushes a branch with an edited beta workflow.
- **Impact:** production Worker/Pages deploy from an unreviewed ref. Practical delta today is small — single-maintainer repo, required reviewers not configured (`POST_MERGE_CHECKLIST.md:64-65`) and branch protection on `main` still open (`:331-332`), so a direct push to `main` is an equally available path. The finding is that the environment gate is a convention, not a boundary, and DEPLOY_ENVIRONMENTS.md / FINDING-009 read as if it were one.
- **Fix:** (1) move `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` into **environment** secrets: `production` for the nine prod jobs + publish/emoji jobs; a new `beta` environment (deployment branches: all except `main`) holding a **separate** token for the three beta jobs — that keeps the production token out of every branch push, though the beta token remains account-wide (true isolation = a second Cloudflare account, out of scope); (2) add a required reviewer on `production` and the `main` ruleset (checklist §2); (3) one sentence in `DEPLOY_ENVIRONMENTS.md` §"Continuous deployment" that the beta split is a workflow convention backed by a shared credential.

### INF-04 — `minimumReleaseAge` is enforced only at resolution; CI's frozen installs never re-check it and Dependabot has no cooldown

- **Severity:** INFO · **Exposure:** LOCAL · **Rotation:** none.
- **Where (CONFIRMED):** `pnpm-workspace.yaml:46` (`minimumReleaseAge: 1440`); all 14 CI installs are `pnpm install --frozen-lockfile` (`ci.yml:76,131`, every `deploy-*.yml`, `publish-packages.yml:123`, `sync-dye-emojis.yml:46`); `.github/dependabot.yml:5-27` has no `cooldown:`.
- **Why:** pnpm applies the age filter while *resolving*; a frozen-lockfile install performs no resolution, so CI trusts whatever the lockfile pins. The 24 h window therefore protects only lockfile changes made by a human running pnpm locally. Dependabot writes lockfiles with its own pnpm invocation — whether that honours the workspace setting depends on the pnpm it runs; there is no repo-side guarantee. (Related policy note: `ci.yml:78` `--audit-level high` lets *moderate* production advisories through green.)
- **Fix:** add `cooldown: { default-days: 1 }` to the npm ecosystem in `dependabot.yml` (mirrors the 24 h policy at the PR source); consider `--audit-level moderate` for the prod audit once the two dev-only overrides are gone.

### INF-05 — Release-announcement webhook has no delivery/replay dedupe: *Redeliver* (or any replay of a signed body) posts the announcement again (cross-unit — discord-worker owns the code)

- **Severity:** INFO · **Exposure:** INTERNET-UNAUTH endpoint, HMAC-authenticated · **Rotation:** none.
- **Where (CONFIRMED):** `apps/discord-worker/src/index.ts:430-536`. Secret = `GITHUB_WEBHOOK_SECRET` (worker secret, shared with GitHub hook `671693119`, `POST_MERGE_CHECKLIST.md:195-197`); body = GitHub `push` JSON, Content-Length and actual-size capped at 1 MiB (`:93`, `:446-461`); HMAC-SHA256 over the raw body, constant-time compare (`src/utils/github-verify.ts:35-83`); only `refs/heads/main` (`:481`); fires when `CHANGELOG-laymans.md` is in `commits[]` or `head_commit` (`:489-498`); fetches `https://raw.githubusercontent.com/${payload.repository.full_name}/main/CHANGELOG-laymans.md` with a 10 s timeout (`:505-507`); posts an embed with the bot token to `ANNOUNCEMENT_CHANNEL_ID` (`:527-532`, `services/announcements.ts:83-94`). No `X-GitHub-Delivery` memory, no "already announced version" memory, no `X-GitHub-Event` check.
- **Observed:** the 5.0 push was delivered/redelivered three times on 2026-08-29 (413 → 200 to the wrong channel → 200 to the right one; the stray post had to be deleted by hand — `POST_MERGE_CHECKLIST.md:206-211`).

- **Fix:** store `X-GitHub-Delivery` in KV with a 24 h TTL and 200-skip duplicates; store the last announced version and refuse to re-announce it; pin `full_name` to `FlashGalatine/xivdyetools` rather than trusting the payload.
