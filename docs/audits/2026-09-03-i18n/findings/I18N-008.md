# I18N-008: the 11 Facewear colour names have no localization path at all — English in all six locales
**Tier:** P2 · **Locale(s):** ja de fr ko zh · **Deploy unit:** core (published) · **Generated?** yes — needs a **new** generator input; `dyenames.csv` cannot express these

## Location
- `packages/core/src/data/facewear_colors.json` — 11 entries shaped `{"id": "silver", "name": "Silver", "hex": "#c0c0c0"}`. One name field, no locale variants.
- `packages/core/src/data/locales/*.json` — the namespaces are `labels, dyeNames, categories, acquisitions, currencies, harmonyTypes, visionTypes, visions, tools, sheets, races, clans`. **There is no facewear-colour namespace.**
- `packages/core/dyenames.csv` carries 125 rows, all real dyes — schema v2 moved facewear out of the dye set, and the localization pipeline was not extended to follow it.

## Evidence
- `categories.Facewear` **is** localized (`Gesichtsschmuck` / `フェイスウェア` / `페이스웨어` / `脸部配饰`), which makes the gap easy to miss: the category heading translates while every colour under it stays English.
- The names are keyed by a string slug (`silver`), not a numeric `itemID`, so `getDyeName()` and the CSV's `itemID`-keyed pipeline cannot reach them even in principle — this is a missing pipeline, not a missing row.
- Consequence: a Japanese user browsing Facewear colours sees a Japanese category header over eleven English swatch names.

## Fix
- Add a slug-keyed source (a second CSV or a block in `localize.yaml`) plus a `facewearColors` namespace emitted by `build-locales.ts`, and a `getFacewearColorName(id, locale)` getter alongside the existing getters.
- Source the names from the game's own Facewear UI per locale rather than translating the English literally.
- Low urgency, but it is the only category in the product where a whole user-visible name set is unlocalized — worth doing with the next core release rather than deferring indefinitely.

## Status
FIXED 2026-09-03 `0957df83` (core 4.3.0) + `1307d783` (web-app) — `facewear-names.csv`, the
`facewearColors` namespace, `getFacewearColorName()`, and the render site that actually uses it.

**The first commit shipped the data and the API but not the fix.** A pre-merge review found
`getFacewearColorName` had **zero production callers**: the one surface that renders a Facewear
tint name, `apps/web-app/src/components/chara-import.ts:1587`, still did `colour.name` —
English, between two localized strings. The finding's own symptom was unchanged. knip cannot
catch this (it does not check class members), and the new core-side test passed because it
tested the getter, not the screen.

Lesson: a getter with a test and no caller is not a fixed finding. Check the render site.
