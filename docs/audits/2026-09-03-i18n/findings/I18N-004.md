# I18N-004: two packages each publish a canonical locale list and two apps still spell it literally; core's own JSDoc still says four locales
**Tier:** P3 (latent — every copy agrees today) · **Locale(s):** all six · **Deploy unit:** api-worker, og-worker, core, bot-logic · **Generated?** no

## Location
- `packages/core/src/services/LocalizationService.ts:32` — `export const SUPPORTED_LOCALES: readonly LocaleCode[]`.
- `packages/bot-logic/src/i18n/types.ts:10` — `export const LOCALE_CODES = ['en','ja','de','fr','ko','zh'] as const` — a second canonical list, in a package that already depends on core.
- Literal re-spellings: `apps/api-worker/src/lib/validation.ts:23` (`VALID_LOCALES`), `apps/og-worker/src/services/translator.ts:17` (inline `for … of [...] as const`).
- `packages/core/scripts/build-locales.ts:67` — a literal, but this runs *before* core is built, so it is defensible.
- `packages/core/src/services/LocalizationService.ts:206` — JSDoc still documents the parameter as `Locale code ('en', 'ja', 'de', 'fr')`, i.e. the pre-ko/zh set.

## Evidence
- `git ls-files … | xargs grep -n "'en', *'ja'"` returns the four lists above; all six codes, all in agreement, so nothing is broken today.
- **Scope corrected mid-audit.** This finding originally also named `apps/discord-worker/src/services/i18n.ts` and `apps/moderation-worker/src/services/i18n.ts` (including a `SUPPORTED_LOCALES` name collision). On the real base both are gone: PR #158's REFACTOR-001 / BUG-001 unified that layer, and each worker now imports `isValidLocale`, `SUPPORTED_LOCALES`, `discordLocaleToLocaleCode` and `resolveUserLocale` from `@xivdyetools/bot-logic/i18n` (`discord-worker/src/services/i18n.ts:41-44`, `moderation-worker/src/services/i18n.ts:23-26`). The drift this finding warns about had already caused BUG-001 and has already been fixed for the bots.
- What is left is therefore mild: two library-level lists and two app literals, versus the four-way split that existed a week ago.

## Fix
- Point `api-worker`'s `VALID_LOCALES` and `og-worker`'s inline list at one exported constant.
- Decide whether `bot-logic`'s `LOCALE_CODES` should re-export core's `SUPPORTED_LOCALES` rather than restate it — low value on its own, worth doing next time either file is touched.
- Fix the JSDoc at `LocalizationService.ts:206` — it has been wrong since ko/zh were added.

## Status
FIXED 2026-09-03 0e5e5ea9 — api-worker and og-worker derive from core's `SUPPORTED_LOCALES`; the stale JSDoc was fixed in core 4.3.0
