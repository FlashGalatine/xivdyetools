# I18N-010: two dead/incorrect entries in core's generator inputs — an authored label that is never emitted, and a French label whose alternates are pasted dye names
**Tier:** P3 · **Locale(s):** all six (`General_Purpose`), fr (`Metallic`) · **Deploy unit:** core · **Generated?** yes — both live in the generator inputs

## Location
- `packages/core/localize.yaml:3` — `General_Purpose: "General-purpose"` (en), with `null` at `:12`, `:21`, `:30` for the other locales; typed at `packages/core/scripts/build-locales.ts:16`.
- `packages/core/localize.yaml:33` — the French `Metallic` entry is a YAML array whose second and third values are `Metallic Silver` and `Metallic Brass` copied verbatim from `dyenames.csv:89` and `:115`.

## Evidence
- `General_Purpose` is authored and typed but `buildLabels()` (`build-locales.ts:228-246`) has no mapping line for it, so no locale's `labels` block contains it — `packages/core/src/data/locales/en.json` has exactly seven label keys (`dye, dark, metallic, pastel, cosmic, cosmicExploration, cosmicFortunes`) and no `generalPurpose`. It has zero consumers. Dead input, not a missing translation.
- The French `Metallic` array produces the right output only because the generator takes index 0; the two trailing values are per-dye names that were pasted into a label slot. Nothing reads them today, so this is a latent trap rather than a live defect — but it will mislead the next person editing that file, and an index change would ship a dye name as a label.

## Fix
- Either wire `General_Purpose` into `buildLabels()` and translate the five nulls, or delete it from `localize.yaml` and from the `build-locales.ts` type. Deleting is the honest option unless a caller is planned.
- Trim the French `Metallic` array to its single real label value.
- Neither changes shipped output, so they can ride along with any other core change rather than justifying a release.
