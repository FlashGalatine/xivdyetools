# I18N-003: core ships a localized tool-name table for 6 of the product's 9 tools that nothing in the monorepo reads
**Tier:** P3 · **Locale(s):** all six · **Deploy unit:** core (published) · **Generated?** yes (`build-locales.ts`), plus the `ToolKey` type in `packages/types`

## Location
- `packages/types/src/localization/index.ts:40` — `type ToolKey = 'harmony' | 'gradient' | 'mixer' | 'swatch' | 'comparison' | 'accessibility'` — the pre-5.0 six, missing budget / extractor / presets.
- `packages/core/src/services/LocalizationService.ts:483,490` and `packages/core/src/services/localization/TranslationProvider.ts:335` — `getToolName()`.
- `packages/core/src/data/locales/*.json` — the `tools.*` namespace, 6 keys × 6 locales.

## Evidence
- `git ls-files '*.ts' | grep -v -E '\.test\.ts$|^docs/' | xargs grep -n getToolName` returns only core's own definitions plus `apps/og-worker/src/og-data-generator.ts:115`, which **defines its own local `getToolName`** and resolves names from `OG_DECK` — it never calls core's.
- web-app has zero `getToolName` call sites; it names tools from its own `tools.*.title` and `resultCard.tools.*` keys.
- Consequence: three surfaces each keep a tool-name vocabulary and core's copy is both stale (6 of 9) and unread — which is why `evidence/vocab-split.txt` shows web-app vs core tool names differing in de/fr/ja/ko/zh. Those rows are **not** user-visible drift; nobody renders core's copy.

## Fix
- Decide the ownership question rather than patching strings: either extend `ToolKey` + `tools.*` to all nine tools and adopt `getToolName()` in web-app and og-worker, or drop the namespace, the getter and the type in the next core major.
- It is published API, so removal is semver-major; leaving it is defensible only if it is documented as external-consumer surface (no `@public` tag is present today).

## Status
FIXED 2026-09-03 `0957df83` (core 4.3.0) — `getToolName` / `ToolKey` marked `@deprecated` rather than removed — published API; removal is a future core major
