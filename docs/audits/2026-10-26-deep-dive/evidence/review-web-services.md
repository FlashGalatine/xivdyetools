## web-services-001 — metric identity and precision disappear in exports and swatch summaries

**BUG / LOW / Logic.** `apps/web-app/src/shared/palette-export.ts:55` defines an entry with a bare `delta` but no matching method. At :158 every finite measure becomes `ΔE ${delta.toFixed(1)}`. The CSS, SCSS and Tailwind serializers all call that formatter (:191, :213, :239). JSON similarly writes `deltaE` rounded to two places (:276-277), and its envelope has no method identity (:258-279).

The values are real method-dependent distances, not pre-normalized common-unit values. `apps/web-app/src/components/gradient-tool.ts:1618` dispatches through `getDistanceForMethod(..., this.matchingMethod)`; the export forwards `step.distance` unchanged at :1062. Mixer forwards its selected-method match distance at `apps/web-app/src/components/mixer-tool.ts:1978`; Extractor forwards its roll distance at `apps/web-app/src/components/extractor-tool.ts:2379`. Their export metadata identifies interpolation/mixing model, not the matching method. Consequently an OKLAB distance 0.024 becomes `ΔE 0.0` in commented formats. A 0.004 value becomes numeric zero in JSON. Even surviving nonzero JSON values lack the method needed to interpret them.

The coordinated component pass independently identified related summary sinks. `apps/web-app/src/components/swatch-tool.ts:805` uses the selected method, but :1938 and :1943 round the selection sentence to one place, and reverse badges round to two at :1045. The locale sentence is generic “sits {delta} away” (`apps/web-app/src/locales/en.json:1291`); **we do not claim its generic Δ badge incorrectly names ΔE**. Its precision still collapses small nonzero values. Core deliberately gives OKLAB three places at `packages/core/src/config/band-vocabulary.ts:50`.

Test gap: `apps/web-app/src/shared/__tests__/palette-export.test.ts:38` has one normal-scale value, 3.42. :53 pins the hardcoded ΔE/one-place comment and :96 pins the two-place JSON value, so the tests affirm the default-path behavior without exercising any metric identity or small OKLAB value. No reproduction was executed. Proposed regression: a real selected-OKLAB export and swatch summary with a nonzero value below 0.05, plus a JSON measure below 0.005. Carry method identity through the payload and use the same method-aware formatting precision as cards. Preserve generic labels where intentional, with the method available nearby/in machine output.

Overlap: component reviewer supplied swatch sinks and left them for this one combined candidate. The earlier local-date export finding is unrelated and its local date helper is now present (`palette-export.ts:140`).

## web-services-002 — stale vote checks resurrect invalidated cache

**BUG / LOW / State.** `apps/web-app/src/services/community-preset-service.ts:292` captures `cacheGeneration`, and :314 protects ordinary cached GET responses against invalidation during the request. However, `hasVoted` uses a separate `vote:<presetId>` cache (:535), performs its own fetch, and unconditionally stores the answer at :559. It has no corresponding generation check.

A successful vote increments the shared generation through `invalidatePresets` and deletes the vote entry (:457-458); unvote does the same at :509-510. A check begun before the mutation can therefore finish after deletion and reinsert the pre-mutation `has_voted` and count. Reopening the detail within the five-minute TTL returns that old answer without a new request. This needs a delayed response, not malformed input or an attacker.

`apps/web-app/src/components/v4/preset-detail.ts:687` and :699 guard the immediate component state, and voting advances that local generation at :800. That protects the current detail from BUG-026, but it cannot stop `hasVoted` caching the stale response: the next mounted detail has a fresh local generation and trusts the service cache. The user sees the old count/button after having already received a successful vote. Server authorization remains authoritative; this is transient UI state drift, graded LOW.

Test gap: `apps/web-app/src/services/__tests__/community-preset-service.integration.test.ts:445` tests delayed list answers across `invalidatePresets`/`clearCache`, but only via `getPresets`. Its `hasVoted` cases at :288-342 cover auth, ordinary success and failed checks. A deferred check → successful vote/unvote → released old check → next check test would expose the missing cache guard. No reproduction was executed. Snapshot generation for `hasVoted` too, cache only when still current, and preferably bind that cache to authenticated identity as well.

Overlap: related to earlier BUG-026 component sequencing and BUG-031 list invalidation, with a distinct remaining service-cache resurrection path. It is not BUG-108's already-fixed failure-answer `vote_count:0` problem.
