# BUG-021: Preset card keyboard handling hijacks its Save and Vote buttons
**Severity:** LOW · **Type:** Logic · **Deploy unit:** apps/web-app · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/web-app/src/components/v4/preset-card.ts:363`
- `apps/web-app/src/components/v4/preset-card.ts:424`
- `apps/web-app/src/components/v4/preset-card.ts:434`

## Evidence
- The focusable article handles every bubbling Enter/Space keydown, unconditionally prevents default and selects the preset. Its nested Save/Vote buttons stop click propagation only. A keyboard activation on either button reaches the article first; it opens details and cancels the button activation. An exact-handler JSDOM probe produced selectedDetail=1 and defaultPrevented=true for Enter dispatched on the child Save button.
- Reproduce: Tab to Save or Vote on a preset card and press Enter or Space. The detail opens instead of saving/voting. Mouse clicks stop propagation and work normally.
- Test gap: preset-card.test.ts:214-243 checks face-button visibility/labels; no keydown coverage exists in the file. The probe exercised the actual extracted handler with DOM bubbling, not a full browser or suite. See [review and verification evidence](../evidence/).

- Correct test path: apps/web-app/src/components/__tests__/v4/preset-card.test.ts:214. Independent verification used static native event semantics; the worker's extracted-handler DOM probe is not a full browser run.
## Fix
- Handle article keyboard activation only when the article itself is the event target, or use a separate open-details button so nested controls retain native keyboard behavior.
