# BUG-018: Harmony ignores canonical harmony type on initialization and reset/import broadcasts
**Severity:** MEDIUM · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/web-app/src/components/harmony-tool.ts:213`
- `apps/web-app/src/components/harmony-tool.ts:339`
- `apps/web-app/src/components/harmony-tool.ts:355`

## Evidence
- The constructor restores selectedHarmonyType and companionDyesCount from legacy keys. onMount reads canonical harmony config but omits both of those fields. The controller subscription updates companions but never selectedHarmonyType. Direct sidebar type edits appear to work because the separate config-change bridge calls setConfig; resetAllConfigs/importConfigs broadcast without that bridge. Sidebar/serialized settings then say complementary (or imported type), while tool rail, wheel and results retain the legacy/current type.
- Reproduce: Choose Triadic, open Advanced Settings and reset settings; return to Harmony results. The canonical/sidebar type is Complementary, but the results/rail remain Triadic. A fresh mount after importing a different type similarly reads the old legacy type. Companion count may initially disagree until a future harmony broadcast.
- Test gap: harmony-tool.test.ts:999-1029 tests direct tool.setConfig(type) and legacy writes; later controller regressions exercise wheel/market. They do not reset/import canonical type and compare sidebar, rail and output. See [review and verification evidence](../evidence/).

- The sidebar mirror intentionally emits no config-change bridge event (config-sidebar.ts:748); direct sidebar edits do not prove reset/import works.
## Fix
- Use the canonical harmony config as the initial authority for type/count, and apply harmonyType through the controller subscription with the existing pin-clearing and regeneration behavior. Avoid redundant full regenerations from the bridge.
