# BUG-011: Glamour adapter records failed Discord edits as successful commands
**Severity:** LOW · **Type:** Error handling · **Deploy unit:** apps/discord-worker · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/discord-worker/src/handlers/commands/glamour.ts:185`
- `apps/discord-worker/src/utils/discord-api.ts:259`
- `apps/discord-worker/src/services/command-trace.ts:235`

## Evidence
- safeEditOriginalResponse catches HTTP/network errors, logs and returnsfalse. Glamour adapter awaits but ignores boolean, so no throw reaches catch/outcome handling. Trace with no mark defaultsok although deferred result was never delivered.
- Reproduce: Have editOriginalResponse return HTTP400/429/500 after successful generation. Adapter resolves; failed edit logged but trace outcome staysok and user has no result.
- Test gap: Add glamour adapter test with safeEdit resolvingfalse and assert failure telemetry and usable fallback/retry policy. glamour.test.ts:16 mocks safeEdit=true; :147 asserts generated payload, without a false delivery case. See [review and verification evidence](../evidence/).

- The failed edit is logged; the incorrect success is command outcome accounting. An expired token may prevent recovery.
## Fix
- Check safeEdit boolean and mark delivery failure; select bounded retry or short fallback. Consider a shared delivery helper to prevent repetition across adapters.

## Status
OPEN — audit only; no implementation change.
