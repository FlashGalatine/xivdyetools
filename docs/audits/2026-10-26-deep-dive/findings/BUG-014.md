# BUG-014: A delayed vote check can repopulate invalidated cache after a vote succeeds
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/web-app/src/services/community-preset-service.ts:535`
- `apps/web-app/src/services/community-preset-service.ts:559`
- `apps/web-app/src/services/community-preset-service.ts:457`

## Evidence
- The shared request() helper snapshots cacheGeneration and refuses to cache answers spanning an invalidation (:292/:314), but hasVoted bypasses that helper and unconditionally caches its response at :559. voteForPreset/removeVote invalidate presets and delete vote:<id> when successful (:457-458/:509-510). A check initiated before that mutation can finish later and reinsert the old has_voted and vote_count for five minutes. The component generation guard avoids applying that late result immediately, but reopening the detail calls hasVoted again and receives the stale cached answer.
- Reproduce: Hold an authenticated GET votes/p/check returning the pre-vote false state; complete POST votes/p successfully; then release the old GET. Close and reopen the preset detail within five minutes. It shows the pre-vote button/count from cache, even though the successful POST response had already updated it. Equivalent sequence exists for removing a vote. Static asynchronous trace only; no runtime repro executed.
- Test gap: services/__tests__/community-preset-service.integration.test.ts:445-457 covers in-flight getPresets answers across invalidatePresets()/clearCache(), but not hasVoted. Its hasVoted cases :288-342 check ordinary success/failure/authentication. preset-detail.ts:696-700 has a tested component generation guard for BUG-026, which hides the immediate overwrite but does not protect the service cache on reopening. See [review and verification evidence](../evidence/).

- Distinct from fixed 2026-09-16-deep-dive/BUG-026 (component guard), 2026-10-04-deep-dive/BUG-031 (list cache) and BUG-108 (failed-check count).
## Fix
- Snapshot cacheGeneration (and preferably authenticated identity) when starting hasVoted, and cache only if unchanged when its response arrives; invalidate on vote mutations/auth changes. Add a deferred check-versus-successful-vote test that verifies a subsequent hasVoted actually fetches fresh state.
