# BUG-023: Editing a preset refreshes the public pool but leaves Mine and its edit baseline stale
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/web-app/src/components/v4/preset-tool.ts:1132`
- `apps/web-app/src/components/v4/preset-tool.ts:943`
- `apps/web-app/src/components/v4/preset-tool.ts:1126`

## Evidence
- The edit-success callback invokes loadPresets only. Mine renders userSubmissions, and opening the edit form resolves its baseline from that same array. It is populated at connection/sign-in and refreshed after deletion or My submissions modal actions, but not after this direct detail edit. After successful edit, Mine can still show the previous title/dyes and reopening Edit uses the old values until another submissions refresh/reload.
- Reproduce: From Mine open an owned preset and edit its name or dyes successfully. Return to Mine: its card still uses the old data. Reopen its Edit form: it is initialized from stale userSubmissions. Contrast delete success, which explicitly refreshes both sources.
- Test gap: preset-tool.test.ts covers Mine first loading at :1321-1350 and votes/history, but contains no edit-success refresh assertion. No suite was run. See [review and verification evidence](../evidence/).

- showTab at preset-tool.ts:1006 refreshes Community/Official only. Owner-visible edited values change even if moderation is pending, so Mine's stale baseline is observable.
## Fix
- Refresh or update userSubmissions on successful edit in addition to the public pool, including pending moderation fields, and assert the next Mine card/edit baseline reflects the authoritative response.

OPEN — audit only; no implementation change.
