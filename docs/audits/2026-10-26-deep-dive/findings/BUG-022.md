# BUG-022: Arming an empty Gradient End slot still writes the picked dye into Start
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/web-app/src/components/gradient-tool.ts:929`
- `apps/web-app/src/components/gradient-tool.ts:1770`
- `apps/web-app/src/components/gradient-tool.ts:1902`

## Evidence
- Clicking the End endpoint arms slot 1 and selectDye forwards that slot to setEndpoint. For an empty selectedDyes array, setEndpoint ignores idx and stores [dye], which is Start. An exact-source method probe of setEndpoint(1,dye) returned [dye] with startDye populated and endDye null. The dense-model comment explicitly says always fills Start first, so the coordinator should reconcile that legacy model rule with the new armed-slot UI contract before filing.
- Reproduce: Clear Gradient, click its empty End card, then pick a dye in the palette. Start fills while End stays empty, despite End being armed.
- Test gap: gradient-tool.test.ts:1509-1545 exercises slot replacement/swaps with a complete existing ramp, never End-first on an empty tool. See [review and verification evidence](../evidence/).

- Confirmed UI promise: enabled TO button and tooltip Click to select end color at gradient-tool.ts:929/934 and en.json:493. Preventing or explaining empty End arming can fix the contract while retaining the dense model; no sparse-model redesign is required.
## Fix
- Either represent a pending End endpoint independently so an armed pick goes into End, or prevent/clearly explain End arming until Start is selected. Preserve serialization and existing no-duplicate rules.
