# BUG-008: Concurrent preview replacements and preset deletion leave uploaded R2 objects orphaned
**Severity:** LOW · **Type:** Race · **Deploy unit:** apps/presets-api · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/presets-api/src/handlers/presets.ts:1191`
- `apps/presets-api/src/handlers/presets.ts:1313`
- `apps/presets-api/src/handlers/presets.ts:1330`

## Evidence
- Upload reads previousKey before image work and overwrites the row unconditionally, deleting only that stale key. Two uploads starting from A store B/C and both delete A; whichever loses its row reference is never removed. UPDATE changes=0 after concurrent preset deletion is also treated as success.
- Reproduce: Synchronize two uploads after both read A; complete B then C. Row points at C, A deleted, B remains indefinitely with no DB reference. Or delete preset between read and UPDATE: upload returns success and stores an unreferenced image.
- Test gap: tests/handlers/presets.test.ts:1865 uploads sequentially (:1895), missing overlapping old-key reads. presets-quotas.test.ts:1160 covers thrown UPDATE, not successful zero-change UPDATE. preview-revision.test.ts covers moderator key binding, not author upload/delete CAS. See [review and verification evidence](../evidence/).

## Fix
- Compare-and-set against captured image state, inspect changes, remove newly stored object on lost/deleted row, and clean only the replaced key for the winning update.

OPEN — audit only; no implementation change.
