# BUG-002: Swatch merges same-index eyes even when live extended colors differ
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** packages/bot-logic · **Covered by test?:** No regression assertion; see evidence.

## Location
- `packages/bot-logic/src/commands/swatch.ts:427`
- `packages/bot-logic/src/commands/swatch.ts:448`
- `packages/core/src/services/chara/chara-library.ts:273`

## Evidence
- Swatch drops rightEye whenever eyesShareIndex and a leftEye row exist, and labels leftEye LR. The facade's flag is expressly index equality. Existing EXT-28 parity fixture has both indices 42, left offGrid #87C0A3 and right palette #DCBA6C while eyesShareIndex remains true. Those two distinct active colors therefore collapse into a single LR match; right color and its nearest dye disappear.
- Reproduce: Pass EXT-28's shared-index/differing-floats document through executeSwatch (see parity fixture around :5669). Expect separate L/R rows because winning colors differ; current :427 skips R. slot:eyes also always selects the first collapsed row.
- Test gap: swatch-library.test.ts:358 tests shared indices only with left matchHex patched to null; ordinary shared-index tests use identical effective colors. Core parity proves the differing-color state but does not exercise command rendering. Static trace only; no suite/repro was executed by reviewer. See [review and verification evidence](../evidence/).

## Fix
- Merge only when both active winning hexes (including composites where relevant) are equal; derive the LR label from that effective-color equality. Add EXT-28 at the command boundary. Publish bot-logic, then deploy bot consumers.
