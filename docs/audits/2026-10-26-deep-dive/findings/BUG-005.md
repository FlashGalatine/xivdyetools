# BUG-005: Concurrent last-slot submissions can both be rolled back while consuming daily quota
**Severity:** LOW · **Type:** Race · **Deploy unit:** apps/presets-api · **Covered by test?:** No regression assertion; see evidence.

## Location
- `apps/presets-api/src/handlers/presets.ts:1075`
- `apps/presets-api/src/handlers/presets.ts:1095`
- `apps/presets-api/src/services/rate-limit-service.ts:379`

## Evidence
- After both calls pass a cap-1 precheck, both INSERT presets and append-only events. Each postcheck counts every event, observes cap+1, and deletes its own preset/votes, but not its event. No insertion-order tie-break on submissions although reserveDailyEvent uses one.
- Reproduce: At 9/10 events, synchronize two different valid palette requests so both recordSubmissionEvent calls complete before either postcheck. Both return 429; neither palette survives; effective count is 11 until midnight.
- Test gap: tests/handlers/presets.test.ts:688 mocks one overshooting request and asserts preset/vote DELETE statements; no second request or surviving append-only event assertion. See [review and verification evidence](../evidence/).

## Fix
- Reserve submission quota atomically or use the event's monotonic id as the final-slot tie-break and release reservations for rolled-back creates.

OPEN — audit only; no implementation change.
