# BUG-001: XIVAuth-only preset authors cannot be banned: both ban entry points require a Discord snowflake and `banned_users.xivauth_id` is never written
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** presets-api (+ moderation-worker) · **Covered by test?** no

## Location
- `apps/presets-api/src/middleware/auth.ts:71-77` — `resolveJWTUserId` falls back to the JWT `sub` UUID for XIVAuth-only accounts; that UUID becomes `author_discord_id` on every preset they submit
- `apps/moderation-worker/src/handlers/commands/preset.ts:521,621`, `handlers/buttons/ban-confirmation.ts:16,86` — every ban target must match `/^\d{17,20}$/` (FINDING-020 / MOD-5), so a UUID author is refused
- `apps/presets-api/src/middleware/ban-check.ts:30-36` — `isUserBanned` reads `discord_id` only; `xivauth_id` is read by `ban-service.ts:174-194,649` but no code path writes it

## Evidence
- Reproduction: sign in with XIVAuth only, submit a preset, `/preset ban_user` on that author → 'must be a Discord snowflake'; a hand-inserted `xivauth_id` row would never match the check either
- `git grep 'INTO banned_users'` → one writer (`ban-service.ts:449`), columns `(id, discord_id, …)`; XIVAuth login is live (`apps/web-app/src/services/auth-service.ts:705`)
- Reviewer row `presets-api-01` (`evidence/review-presets-api.md`), re-framed by the coordinator and confirmed by the Opus pass (`evidence/verifier-pass.md`)

## Fix
- Decide the identity key for bans: either (a) let moderation-worker ban any `author_discord_id` value it read from `presets` (relax the snowflake gate to snowflake-or-UUID at the two gates + the autocomplete), or (b) write `xivauth_id` on ban and make `isUserBanned` check `discord_id = ? OR xivauth_id = ?`
- (a) is one moderation-worker deploy; (b) is a presets-api + moderation-worker pair. Either way add a ban-check test that binds a UUID (closes BUG-043)
