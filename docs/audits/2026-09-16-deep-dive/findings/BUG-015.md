# BUG-015: `text_edit` / `flagged_edit` / `preview_upload` daily caps are check-then-insert; concurrent requests can overshoot the cap
**Severity:** LOW · **Type:** Race · **Deploy unit:** presets-api · **Covered by test?** no

## Location
- `apps/presets-api/src/services/rate-limit-service.ts:168-200` — `checkDailyEventLimit` counts, the handler acts, then `recordSubmissionEvent` inserts; no post-insert re-check or rollback, unlike the hardened `submission` cap

## Evidence
- Reviewer row `presets-api-04`; soft quota, overshoot bounded by request parallelism — hence LOW

## Fix
- Mirror the `submission` shape: insert first, count including the new row, roll back (delete the event + the mutation) when over
