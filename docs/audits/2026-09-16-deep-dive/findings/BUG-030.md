# BUG-030: Preset edit form drops unresolvable stored dye ids at load and would then send a shortened `dyes` patch on a Save with no edits
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** web-app · **Covered by test?** no

## Location
- `apps/web-app/src/components/preset-edit-form.ts:117-119` — `.map(resolvePresetDye).filter(Boolean)`
- `apps/web-app/src/components/preset-edit-form.ts:698` — `dyes.join(',') !== preset.dyes.join(',')` → `updates.dyes`

## Evidence
- Latent today: `dyes.json` holds exactly stainIDs 1–125 and `resolvePresetDye` (`dye-service-wrapper.ts:57-63`) resolves every one; only an out-of-DB 126–254 id (which presets-api accepts) or a DB shrink triggers it, and `MIN_DYES` (721) stops a total wipe
- Reviewer row `webapp-modals-05`; Opus pass confirmed LOW (latent)

## Fix
- Keep the original id list as the diff baseline (compare against the resolved-and-kept ids), and refuse to save when any stored id failed to resolve

FIXED 2026-09-16 74f19f75 — dyes diffed against the resolved baseline; a change while an id is unresolved is refused with `preset.validation.dyesInvalid`, other fields still save
