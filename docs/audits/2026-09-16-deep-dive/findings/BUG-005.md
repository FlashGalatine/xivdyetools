# BUG-005: Browser Back from a preset detail remounts `<v4-preset-tool>` and loses tab, search and scroll because `pushState` omits `toolId`
**Severity:** MEDIUM · **Type:** State · **Deploy unit:** web-app · **Covered by test?** no

## Location
- `apps/web-app/src/components/v4/preset-tool.ts:762-766` — `window.history.pushState({ preset: id }, '', '/presets/:id')`, no `toolId`
- `apps/web-app/src/services/router-service.ts:356-375` — `handlePopState` falls back to `parseCurrentPath()` and notifies unconditionally
- `apps/web-app/src/components/v4-layout.ts:316-321,658-668` — `loadToolContent('presets')` clears the container and `createElement('v4-preset-tool')` with no same-tool skip

## Evidence
- Reproduction: Presets → switch tab / type a search / scroll → open a preset → Back: tab (`preset-tool.ts:92`), `searchQuery` (132), scroll and the loaded pool reset and refetch
- Reviewer row `webapp-v4-22`; Opus pass confirmed by tracing popstate through the router and the layout

## Fix
- Either push `{ toolId: 'presets', preset: id }` and have `handlePopState` skip the notify when the tool is unchanged, or make `loadToolContent` a no-op for same-tool popstate (the shell already knows the mounted tool)
- Regression test: pushState → popstate → assert the same element instance survives

## Status
FIXED 2026-09-16 554fd745 + 1ad6d3dd, reshaped 2026-09-18 8395eb59 — `{ toolId }` in pushState, URL-resolved popstate with `_restoreSeq` guard; the same-tool skip first lived in the router (which also silenced harmony-tool's `?dye=` re-read — PR-review catch), and now the router always notifies with `sameTool: true` while v4-layout alone skips its remount. Residual: tab, search and the loaded pool survive Back; scroll does not (the detail replaces the grid DOM, nothing saves `scrollTop`) — file separately if wanted
