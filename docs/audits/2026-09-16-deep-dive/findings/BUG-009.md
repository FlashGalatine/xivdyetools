# BUG-009: `ColorConverter.hexToHsv` consults the LRU before validating, so a bare `'FF0000'` throws cold and succeeds warm
**Severity:** LOW · **Type:** Logic · **Deploy unit:** core · **Covered by test?** no

## Location
- `packages/core/src/services/color/ColorConverter.ts:445-455` — cache lookup keyed by `normalizeHexKey` (197-205, strips `#`) returns before `hexToRgb` (208-214) runs `isValidHexColor`
- `packages/core/src/constants/index.ts:116` — `PATTERNS.HEX_COLOR` requires the `#`

## Evidence
- `hexToHsv('#FF0000'); hexToHsv('FF0000')` → HSV; fresh instance: `hexToHsv('FF0000')` → `AppError INVALID_HEX_COLOR`. The warm value is the correct colour, so this is a consistency defect only
- Reviewer row `core-color-01`; Opus pass confirmed LOW

## Fix
- Validate before the cache lookup (one `isValidHexColor(hex)` guard at the top), mirror in `hexToLab`/`hexToOklab` if they share the shape; add a cold-vs-warm test

## Status
FIXED (Sprint 8, `6b9c4ec0`) — `hexToHsv` validates before the LRU lookup; the six other `hexTo*` entries already delegate to a validating `hexToRgb` and needed nothing. Cold-vs-warm tests; the plan's pre-merge grep (no app passes an unprefixed hex) was clean.
