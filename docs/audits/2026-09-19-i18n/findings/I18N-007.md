# I18N-007: core's locale generator silently emits English for an empty CSV cell, and `getColorWheelName` falls back to the raw id (both latent)
**Tier:** P3 (latent) · **Locale(s):** all · **Deploy unit:** core (published) · **Generated?** yes — this IS the generator

## Location
- `packages/core/scripts/build-locales.ts:277` (`buildDyeNames`) and `:297` (`buildFacewearNames`) — `row[nameColumn]?.trim() || row[fallbackColumn]?.trim()`; no warning, no non-zero exit.
- `packages/core/src/services/localization/TranslationProvider.ts:266` — `… ?? id`; sibling getters (`getHarmonyType` `:256`) end in `this.formatKey(key)`, so a miss there reads "Oklch Hue", here it reads `oklch-hue`.

## Evidence
- Today nothing is wrong: a python scan of `dyenames.csv` found 0 empty cells, 0 non-en cells identical to en, 0 within-locale duplicates across 125 × 5 (`evidence/review-core-svg.md`). But ko/zh cells are pasted by hand for every new dye, and a blank one would ship as English with every gate green — the same class as 2026-09-03's `Perlmutt-`.

## Fix
- Generator: collect empty cells and `process.exit(1)` listing them (an explicit `--allow-missing` for work in progress). Getter: end in `formatKey(id)`. No published signature changes.
