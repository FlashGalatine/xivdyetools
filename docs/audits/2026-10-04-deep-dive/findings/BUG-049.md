# BUG-049: preferences.ts getAffectedCommands and the /preferences schema advertise consumers that never read the key (clan/gender, blending->/gradient, matching->/swatch, and /harmony is left out)
**Severity:** LOW · **Type:** Logic · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** packages/bot-logic (en.json preferences.descriptions.clan/gender option strings)

## Location
- `apps/discord-worker/src/services/preferences.ts:637`

## Evidence
- Reproduction: /preferences set blending:oklab -> embed says it affects /mixer and /gradient; /gradient still interpolates in HSV. /preferences set clan:Raen -> says it affects /swatch; /swatch output is unchanged because it reads the .chara file
- Nothing outside the writers (services/preferences.ts:194,197) reads clan or gender. swatch.ts:61 reads only theme. gradient.ts:39-40 defaults color_space to 'hsv' and never calls resolveBlendingMode, which only mixer-v4.ts:68 calls. harmony.ts:80 reads matching but is missing from the list. The set handler (handlers/commands/preferences.ts:375) puts these strings in the success embed.
  - Checked: grep prefs.clan/prefs.gender/resolveBlendingMode in apps/discord-worker/src returns only the writers and mixer-v4.ts:68; swatch.ts:61; gradient.ts:36-41; schemas.ts:674,681 ('Default clan/gender for /swatch')
- Second, independent check (severity LOW): I could not refute the defect, but I would grade it LOW, not MEDIUM. Each claim checks out in the code. getAffectedCommands (apps/discord-worker/src/services/preferences.ts:633-660) maps blending to /mixer and /gradient, matching to /swatch, and clan/gender to /swatch. The /preferences set handler (apps/discord-worker/src/handlers/commands/preferences.ts:375, rendered at about :421) puts those strings into the success embed. In practice gradient.ts:39-40 takes color_space from its own option, defaulting to 'hsv', and never reads prefs.blending. resolveBlendingMode is called only at mixer-v4.ts:68. swatch.ts:61 reads only prefs.theme, and SwatchInput gets its data from the .chara file. Outside the writer, nothing reads prefs.clan or prefs.gender. harmony.ts:80 does call resolveMatchingMethod, but harmony is missing from the matching list. The origin is MAIN, and the dead-code audit does not cover this, so it is not a duplicate. Why LOW: every command still produces correct output for its own inputs. The defect is the confirmation embed and the option descriptions (schemas.ts:674,681; en.json:1139,1142) claiming effects that never happen, plus clan/gender settings that do nothing. That is misleading text, which the brief's scale calls cosmetic (LOW). It is not a wrong result on a computation path (MEDIUM).
- Origin: git show 8ecb878f:apps/discord-worker/src/services/preferences.ts lines 633-645 match HEAD exactly

## Fix
- Trim getAffectedCommands: blending -> /mixer; matching -> add /harmony, drop /swatch. Then either remove the clan/gender options or wire a reader, and add a key-to-handler table test. Dropping the bot-logic locale strings needs a bot-logic publish, then a discord-worker deploy.
