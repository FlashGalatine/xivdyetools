# BUG-059: og-data-generator.ts generateOGDataForTool: gradient/mixer/harmony crawler ignores hexStart/hexEnd/hexA/hexB/hex slots, so a custom-colour share unfurls the generic tool card
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** apps/og-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/web-app (share grammar)

## Location
- `apps/og-worker/src/og-data-generator.ts:825`

## Evidence
- Reproduction: Crawler GET /gradient/?hexStart=ff8800&end=43&steps=5 -> start=0 -> toolDefault('gradient'): generic title, /gradient/default.png, og:url /gradient/ with no params
- Real: the web emits hexStart/hexEnd (gradient-tool.ts:1678-1685), hexA/hexB (mixer-tool.ts:1923-1926) and hex (harmony-tool.ts:1853), but the crawler reads only start/end, dyeA/dyeB and dye (og-data-generator.ts:815,825-826,836-837). A missing slot parses to 0, getDyeInfo(0) is null, and the result is toolDefault, whose og:url has no params (:184-193). Graded LOW, not MEDIUM: it only affects custom colours, and the degrade is honest (a generic card, no false dye). Budget documents the same degrade at :580-581.
  - Checked: og-data-generator.ts:293-303 (gradient null branch), :825-826 (parseInt(get('start')||'0')); gradient-tool.ts:1678-1685; git grep hexStart in apps/og-worker returns nothing
- Origin: git show 8ecb878f: og-data-generator.ts:825 has the same start parse; gradient-tool.ts:1681 already emits hexStart; mixer-tool.ts:1924 emits hexA; harmony-tool.ts:1853 emits hex

## Fix
- og-worker only. Pin the degrade with a test and document it in CLAUDE.md for gradient/mixer/harmony, as budget does. Optionally keep the share params on og:url. Rendering hex endpoints would need an allowlist/cache-key ruling (S7-R7/R10).
