# BUG-013: A stale preserved ?dye= deep link overrides the user's later choice in Budget (Set as budget target) and Harmony (base-dye pick)
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

- `apps/web-app/src/components/harmony-tool.ts:454` — harmony-tool.ts handleDeepLink: a stale preserved ?dye= overrides the user's later base-dye pick

- Second, independent check (severity MEDIUM): I could not refute it, and MEDIUM is the right severity. The bug path is deterministic. After a share link or an 'Inspect in Harmony' hand-off puts ?dye=X in the URL, a base dye the user then picks only reaches storage; nothing rewrites the URL, and every tool switch carries dye= forward. When the user comes back, Harmony is rebuilt: it first restores their own pick from storage, then the deep-link handler overwrites it with the old URL dye and saves that over it. The user sees the wrong base dye and loses their own pick and any pinned dyes. No data is lost, and the bug needs a dye= already in the URL, an in-tool change, then leaving and returning. That makes it an edge path rather than a common one, so it is not HIGH. It is also not LOW, because nothing else prevents it.
- Origin: git diff --stat 8ecb878f HEAD -- result-card.ts, router-service.ts, budget-tool.ts: empty

## Fix
- Route setAsBudgetTarget through handoffTo('budget', dye) with budget:'dye' added to HANDOFF_PARAM (shared/tool-handoff.ts), so the explicit param wins over the preserved one. Web-app only.
- On a base-dye change, replaceRoute('harmony', {dye: stainID}) (or delete dye from the URL), so the preserved param tracks the current pick.
