# BUG-040: XIVAPI_VERSION="latest" makes the chara row-cache namespace constant, so a patch never cold-starts the cache
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/api-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/api-worker/wrangler.toml:113`

## Evidence
- Reproduction: After a patch adds an Item row that shares a cached ModelMain, /v1/chara/resolve keeps serving the pre-patch row family (missing the new twin) for up to 7 d + 1 d SWR
- Both envs set XIVAPI_VERSION="latest" (wrangler.toml:47 and :113), and CharaRowCache's prefix is `chara:3:${client.versionKey}`, the literal env string (cache.ts:41, router.ts:203). The namespace never changes across patches, so the 'roll forward = cold cache' design (cache.ts:5-7) cannot happen and rows (including cached-empty 'no item row') persist up to TTL+SWR. The claim that `latest` 503s during ingest is unverified.
  - Checked: wrangler.toml:47/:113 XIVAPI_VERSION = "latest"; xivapi.ts:216-222 versionKey returns the env string.; cache.ts:41 prefix uses gameVersion; cache.ts:20-24 TTL 7 d + SWR 1 d; getRows ignores staleness.; CLAUDE.md:136 documents the pin as 'latest or a /api/version key', but the cache design assumes a real key.
- Origin: git show 8ecb878f:apps/api-worker/wrangler.toml lines 44 and 87 both set XIVAPI_VERSION = "latest"

## Fix
- Pin a real /api/version key in [env.production].vars and bump it with the post-patch table rebuild, or derive the namespace from the search response's version. No package publish is needed.
