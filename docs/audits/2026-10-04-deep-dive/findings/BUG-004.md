# BUG-004: A preset submitted or edited through the bot is posted twice: discord-worker's own moderation/submission-log post (legacy button ids) plus the presets-api webhook's revision-bound post
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/presets-api

## Location
- `apps/discord-worker/src/handlers/commands/preset.ts:576`
- `apps/discord-worker/src/handlers/commands/preset.ts:575` — preset.ts processSubmit/EditCommand duplicates the presets-api webhook moderation and submission-log posts
- `apps/discord-worker/src/index.ts:402` — discord-worker preset webhook + bot-side notifyModerationChannel/notifySubmissionChannel both post for bot submissions and edits
- `apps/presets-api/src/handlers/presets.ts:1089` — presets-api webhook + discord-worker bot-side posts both fire for bot submissions/edits -> duplicate moderation and submission-log embeds
- `apps/presets-api/src/handlers/presets.ts:1077` — presets-api webhook + discord-worker /preset submit/edit both post the same submission to the moderation/submission-log channels
- `apps/discord-worker/src/index.ts:402`

## Evidence
- Reproduction: /preset submit of flagged text -> pending -> two moderation embeds; legacy one only refreshes, the other goes stale after the first decision; auto-approved bot submits also double-post to the submission log (notifySubmissionChannel + index.ts ~440).
- Bot submit/edit calls its own notifyModerationChannel/notifyEditModerationChannel (preset.ts:576,:924; no contentRevision -> legacy ids) and presets-api calls notifyDiscordBot unconditionally (presets.ts:868,:1090; no source filter in notifyDiscordBot); the webhook (index.ts:402) posts a second, bound embed from the same MODERATION_CHANNEL_ID.
  - Checked: git grep 8ecb878f shows preset.ts:576/:924 + presets.ts:825/:1037 notifyDiscordBot + index.ts:402; notification-service.ts:177-186 has no source check; preset-notifications.ts:100-121 falls back to legacy when contentRevision undefined.
- Second, independent check (severity MEDIUM): I could not refute it, and MEDIUM is the right severity. A /preset submit that lands as pending sends two moderation posts to MODERATION_CHANNEL_ID, and a pending /preset edit does too. Nothing on the path filters by source or deduplicates. The duplicate cannot cause a wrong moderation decision, because legacy ids only refresh and bound ids carry a revision, so this is not HIGH. It is more than cosmetic, though. For bot edits, the only embed that shows the diff and the Revert button is the legacy copy, whose first click acts on nothing. The bound copy from the webhook is a plain "new pending" embed with no Revert, and it goes stale once the first decision is made. That is an operational risk on an edge path. Clean bot submissions also post twice to SUBMISSION_LOG_CHANNEL_ID; on its own that part would be LOW.
- Found independently from another slice: processSubmitCommand posts its own embeds: preset.ts:571 notifySubmissionChannel and :576 notifyModerationChannel, which uses legacy ids with no contentRevision (:1142-1150). presets-api POST /presets also calls notifyDiscordBot for every caller, bot included (presets.ts:1077-1091, source: auth.authSource), and the webhook then posts a second embed (index.ts:402-404 if pending, :446-456 if approved). Edits are doubled only when the edit changes text or is flagged (presets.ts:841-846). For a non-text edit to an already-pending preset, the bot's legacy embed is the only post.
- Found independently from another slice: Real on this code: both paths fire unconditionally for bot-authenticated submits/edits. Operational duplicate in the mod channel (the bot copy carries legacy ids that only refresh), not data loss, so MEDIUM.
- Found independently from another slice: presets-api fires the webhook for every created row, with no source filter. discord-worker's webhook posts pending presets to MODERATION_CHANNEL_ID and approved ones to SUBMISSION_LOG_CHANNEL_ID. After that response the bot posts again (notifySubmissionChannel / notifyModerationChannel, legacy ids). Approved-preset bot edits whose text gets flagged double the same way through notifyEditModerationChannel.
- Found independently from another slice: presets-api posts a webhook on every submit and edit with no check on authSource (presets.ts:1077 for submit, ~853 for edit), and the bot's command handler also posts to the same channels (preset.ts:571/576/924). sendModerationNotification has no idempotency guard, so a bot submission or edit produces two posts.
- Found independently from another slice: preset.ts:571/576/924 post the submission-log or moderation embed from the bot side. presets-api presets.ts:1077-1091 (submit) and :845-870 (edit) also call notifyDiscordBot with no authSource filter (it is gated only on the DISCORD_WORKER binding and the secret), and index.ts:402 (pending) and :446 (approved) post a second copy. The webhook is live in production because web submissions depend on it.
- Origin: git grep at 8ecb878f: discord-worker preset.ts:576,:924 notify calls; presets-api presets.ts:825,:1037 notifyDiscordBot; discord-worker index.ts:402 pending webhook branch. PR-#227 only made the bot copy legacy-refresh-only.

## Fix
- Drop the bot-side moderation/submission-log posts (presets-api notifies for both sources), or skip one when source==='bot'. If kept for Revert/diff, pass the post-write content_revision. No package publish.
