# BUG-134: ColorAccessibility.isLightColor/getOptimalTextColor use a luminance threshold of 0.5, which picks the lower-contrast text for luminance between about 0.18 and 0.5
**Severity:** LOW · **Type:** Logic · **Deploy unit:** packages/core · **Covered by test?** partly · **Origin:** MAIN

## Location
- `packages/core/src/services/color/ColorAccessibility.ts:72`

## Evidence
- Reproduction: ColorService.getOptimalTextColor('#FF8000') -> '#FFFFFF' (contrast ~2.5:1 vs ~8.3:1 for black)
- For #FF8000 (L about 0.367), isLightColor returns false, so the text is white at about 2.5:1 while black gives about 8.3:1. This is published ColorService API with no in-repo caller: web-app budget-tool has its own private isLightColor. 2026-10-04-dead-code/DEAD-048 is KEEP, not REMOVE, so this finding is not superseded. LOW because it is latent.
  - Checked: git grep isLightColor/getOptimalTextColor: only the ColorService.ts:268/275 facade outside tests; 2026-10-04-dead-code/DEAD-048 status KEEP
- Origin: git show 8ecb878f:packages/core/src/services/color/ColorAccessibility.ts:72 `return luminance > 0.5;`

## Fix
- getOptimalTextColor: return whichever of black/white has the higher getContrastRatio (equivalently, luminance > ~0.179). Needs a @xivdyetools/core publish; no in-repo consumer deploy needed.
