# BUG-036: PaletteService kMeansClustering caps k at pixel count, so images with fewer distinct colours than colorCount return duplicate 0-pixel clusters that discord /extractor renders as rows
**Severity:** MEDIUM · **Type:** Edge case · **Deploy unit:** packages/core · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/discord-worker (extractor.ts:525-556 consumer), packages/svg (bandSlices MIN_SLICE floor)

## Location
- `packages/core/src/services/PaletteService.ts:272`

## Evidence
- Reproduction: A PNG at or under maxDimension (no Lanczos resize, so no edge colours) with 2 opaque colours, run with colorCount 4: the result is [red 50, blue 50, red 0, red/blue 0], and the card shows two fabricated 0% rows
- Once every distinct colour is a centroid, k-means++ :166-168 picks a duplicate pixel. Strict < in assignToClusters gives the clone 0 pixels and updateCentroids keeps it. discord extractor.ts:525-556 has no pixelCount filter: dedupe swaps each clone to a 'next best' dye, bandSlices gives it 7px, and the count inflates. web-app filters it and documents this exact case at extractor-tool.ts:2145-2158.
  - Checked: PaletteService.ts:166-168, :272 effectiveK=min(k,pixels.length), :186-205 strict < assignment; extractor.ts:525-556 has no filter; web-app extractor-tool.ts:2145-2158 comment plus .filter(pixelCount>0)
- Second, independent check (severity MEDIUM): I could not refute this. I traced the code path and reproduced it. At PaletteService.ts:272, effectiveK = min(k, pixels.length) caps k by pixel count, not by distinct colours. Once every distinct colour is already a centroid, the total squared distance is 0 and :166-168 picks a random pixel, which is a duplicate centroid. assignToClusters (:213-218) uses strict <, so ties go to the lower index and the clone gets 0 pixels. updateCentroids (:242-244) keeps the empty clone, and extractPalette (:420-427) returns it with dominance 0 and pixelCount 0. Nothing downstream filters it out. extractAndMatchPalette (:459-485) still matches a dye for it. In discord extractor.ts:525-559, dedupe (:111-156) swaps the duplicate dye for the next-best dye, and the result is added to both band and rows. The svg bandSlices MIN_SLICE=7 (palette-grid.ts:105-118) then gives it a visible slice. The embed count at :589 also says "4 colours", so the I18N-006 comment there, which says matches.length===1 is reachable for a near-monochrome image, is wrong. The input is reachable from Discord: MIN_COLORS is 3 and the default is 4 (extractor.ts:68-74), so any lossless image with fewer distinct colours than that triggers it. That covers flat icons or pixel art up to 256px (no resize), and solid-colour images at any size, since a Lanczos resize of a single colour stays a single colour. No test covers it: the core tests always set colorCount equal to the number of distinct colours, the clamp test (PaletteService.test.ts ~131-140) only asserts length ≤10 / ≥1, and the discord tests mock extractAndMatchPalette. Origin is MAIN. I am keeping MEDIUM rather than LOW because the card shows made-up dye recommendations and a wrong colour count, not just cosmetic noise. I am not raising it to HIGH because it needs a flat-colour lossless image; photos and JPEGs produce many distinct colours.
- Origin: git show 8ecb878f:packages/core/src/services/PaletteService.ts has effectiveK at :272. git log 8ecb878f..HEAD -- packages/core apps/discord-worker/src/handlers/commands/extractor.ts is empty.

## Fix
- Drop pixelCount===0 clusters in core extractPalette (or cap k at the distinct-colour count) and assert the exact result. Needs a @xivdyetools/core publish, then consumer deploys.
App-only alternative: filter pixelCount>0 in discord-worker extractor.ts before dedupe; no publish needed.
