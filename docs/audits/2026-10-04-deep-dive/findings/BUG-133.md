# BUG-133: chara-parser parseFloatColor accepts empty segments as 0 (and Infinity), producing a silent wrong lip/colour
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** packages/core · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/web-app

## Location
- `packages/core/src/services/chara/chara-parser.ts:237`

## Evidence
- Reproduction: MouthColor "0.2,0.3,0.4," -> alpha 0 -> lip slot verdict inert/noLip instead of a parse error
- chara-parser.ts:237 maps Number('') to 0, so "0.2,0.3,0.4," passes the NaN check as 4 parts with alpha 0 and resolver :345 marks the lip inert/noLip; this contradicts the function's own doc promise to throw loudly on malformed values. Hand-edit only.
  - Checked: chara-parser.ts:222-250 (doc: throws loudly on malformed); chara-resolver.ts:344-347 (alpha 0 -> noLip)
- Origin: git grep at 8ecb878f: chara-parser.ts:237 `value.split(',').map((p) => Number(p.trim()))` identical; no diff 8ecb878f..HEAD

## Fix
- Reject a part when p.trim()==='' or !Number.isFinite(n) in parseFloatColor. Needs a @xivdyetools/core publish, then consumer deploys.
