# BUG-139: HarmonySelector.test.ts pin test pins Jet Black, a dye no earlier slot picks, so it cannot detect the earlier-slot duplicate
**Severity:** LOW · **Type:** Untested behavior · **Deploy unit:** packages/core · **Covered by test?** no · **Origin:** MAIN

## Location
- `packages/core/src/services/dye/__tests__/HarmonySelector.test.ts:200`

## Evidence
- Reproduction: Replace the pin with slot 0's natural dye (Cactuar Green): two slots show it and BUG-137 reproduces, but the shipped test stays green
- The test pins slot 1 of a Dalamud Red triadic to Jet Black, which slot 0 never chooses. Its `toHaveLength(1)` uniqueness assertion therefore passes regardless of order, while BUG-137 shows the bug when the pin equals slot 0's natural pick.
  - Checked: HarmonySelector.test.ts:200-214 (Jet Black pin, uniqueness check)
- Second, independent check (severity LOW): The test gap is real, so the finding is not refuted. In triadic, slot 1 is the last slot, and Jet Black is never slot 0's pick, so the uniqueness assertion at HarmonySelector.test.ts:213 can never fail. The comment there says "a later slot cannot reuse it", but no later slot exists. No other test reserves a pin against earlier slots: the golden tests don't, and the web-app harmony-tool.test.ts only checks that pins clear when the wheel changes. The underlying defect (BUG-137) is also real. In HarmonySelector.ts, `used` gets a pin's id only when the loop reaches that pin's slot, so earlier slots can still pick that dye. However, the single-render path that BUG-137 describes cannot happen in the UI. Swaps come only from a slot's companion list (harmony-tool.ts:1524/1629). Under preventDuplicates those companions already leave out the dyes earlier slots chose, and pins at later slots never change earlier slots. A search found no duplicate from that path. The duplicate needs an extra step: a swap, then a config change the web app keeps pins across (dedup toggle, ΔE method, perceptual toggle, filters; only a wheel, type or base change clears them, harmony-tool.ts:385-396). Even then the harm is one dye shown twice in the palette. A test gap for an edge path that needs a swap plus a setting change, with only display harm, is LOW, not MEDIUM.
- Origin: git log 8ecb878f..HEAD -- packages/core/src/services/dye is empty; the test is unchanged at main

## Fix
- Add a case: compute unpinned slots, pin a later index to slot 0's dye with preventDuplicates:true, assert all slot dyes are unique. Test-only, but ships with the BUG-137 fix (core publish).
