# BUG-047: Favourites name back-fill converts any getPreset failure (5xx/timeout/429, swallowed by .catch(()=>null)) into the preset UUID as the persisted name, which is never retried; names also never refresh on rename and the whole-list write can lose a concurrent favorite add.
**Severity:** LOW · **Type:** Error handling · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/discord-worker/src/index.ts:1292`
- `apps/discord-worker/src/index.ts:1296` — getFavoritedPresetsAutocompleteChoices persists the preset UUID as its name when getPreset throws

## Evidence
- Reproduction: Legacy v1 favourites user types in /preset favorite remove while presets-api returns 5xx or times out -> entries saved as {id, name:<uuid>}; autocomplete shows UUIDs forever and the text filter cannot match them
- getPreset (preset-api.ts:237-246) returns null only on a 404 and rethrows 5xx, timeout and 429. index.ts:1291-1295 swallows the error with .catch(()=>null) and sets name = id, and :1306 persists it. Because the back-fill selects entries by !e.name, the UUID name is never retried, so wrong data stays in KV durably. The rename and concurrent-add points are the earlier-audit OPT-007 design and the known KV read-modify-write limitation, so they are not graded.
  - Checked: index.ts:1287-1306; services/preset-api.ts:237-246; services/preset-favorites.ts:67-98 (v1 -> name '')
- Second, independent check (severity LOW): The defect is real. getPreset (apps/discord-worker/src/services/preset-api.ts:237-246) returns null only on a 404 and rethrows 5xx and timeout errors. index.ts:1292-1296 turns any rejection into null and sets name = id. The block at :1306-1311 then persists it. The back-fill selects entries by !e.name, so a UUID name is never retried. Nothing else rewrites names: the only other writers are addPresetFavorite, which takes preset.name from preset.ts:1238, and removePresetFavorite. The same line is in main@8ecb878f (index.ts:1295) and no test covers the thrown-lookup path. I grade it lower than MEDIUM for four reasons. (1) Only a user still on a pre-(earlier-audit OPT-007) (2026-07-18) v1 blob who has not opened /preset favorite remove autocomplete in about 2.5 months can hit it. That group only shrinks, because the first successful autocomplete migrates them for good. (2) presets-api has to fail or pass its 10 s timeout on exactly that first migrating keystroke. (3) The harm is a display label only. Each entry keeps its correct preset id, removal by value still works, and the empty-query list still shows up to 25 entries. Typing a name finds nothing, but typing the UUID still matches. (4) It fixes itself when the user removes the favourite and adds it again. On the brief's scale that is cosmetic or latent, so LOW, not a wrong result on an edge path.
- Found independently from another slice: The chain is airtight in code: a non-404 failure becomes null, the id is written as the name, and the empty-name filter never selects it again. Edge path (legacy v1 users during an outage), but the wrong name persists, so MEDIUM.
- Origin: git show 8ecb878f:apps/discord-worker/src/index.ts line 1295 'missing[i].name = resolved[i]?.name ?? missing[i].id'

## Fix
- Persist names only from successful lookups. A null (404) may use a placeholder; a thrown lookup leaves name '' so the entry is retried. Skip the write when nothing resolved.
