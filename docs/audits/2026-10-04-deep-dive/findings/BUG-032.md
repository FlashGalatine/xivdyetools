# BUG-032: preset-submission-service.deletePreset failure reported as success by both callers
**Severity:** MEDIUM · **Type:** Error handling · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/web-app/src/services/preset-submission-service.ts:471`

## Evidence
- Reproduction: Delete own preset while API answers 403/429/5xx or network drops -> 'deleteSuccess' toast, dialog dismissed, preset still exists
- deletePreset (preset-submission-service.ts:471-503) catches everything and returns {success:false}; preset-tool.ts:982-989 and my-submissions-modal.ts:213-216 await it, ignore the result, toast deleteSuccess and close/reload, so their catch branches are unreachable.
  - Checked: preset-submission-service.ts:493-502 returns {success:false}; preset-tool.ts:984 and my-submissions-modal.ts:214 discard the return value
- Second, independent check (severity MEDIUM): I could not refute it. deletePreset (preset-submission-service.ts:471-503) never throws. It returns {success:false} in three cases: the client-side auth check fails (:472-474), the response is not OK (:493-496), and the catch-all fires (:500-502). Both callers ignore the return value and show deleteSuccess: my-submissions-modal.ts:214-217 (toast, then dismiss the confirm dialog and call onChanged) and preset-tool.ts:984-989 (toast, reload, clear the selection, pushState). So their catch branches cannot run. MEDIUM holds: the user gets a false success on an edge path and no data is lost. The list reload still shows the preset, but the user has been told it is gone while it stays public.
- Origin: git log 8ecb878f..HEAD -- apps/web-app/src/services/ preset-tool.ts my-submissions-modal.ts is empty; code identical at main

## Fix
- Callers check result.success and toast errors.deletePresetFailed (keep the modal open) on false, or make deletePreset throw on non-OK; web-app only, no package publish.
