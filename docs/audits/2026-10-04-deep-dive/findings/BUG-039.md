# BUG-039: router.ts SERVICE_BINDING_BUDGET_MULTIPLIER can drift from the UNIVERSALIS_SERVICE_RATE_LIMITER binding with no failing test
**Severity:** LOW · **Type:** Untested behavior · **Deploy unit:** apps/api-worker · **Covered by test?** no · **Origin:** PR-#229 · **Other units:** none

## Location
- `apps/api-worker/src/universalis/router.ts:125`

## Evidence
- Reproduction: Set the router multiplier from 20 to 1: router.test.ts and wrangler-config.test.ts still pass, while the service-scope X-RateLimit-Limit and the KV-fallback budget silently become 30 instead of 600
- On the binding path, SERVICE_BINDING_BUDGET_MULTIPLIER (router.ts:125, not exported) only feeds the single tier's reported limit and the KV-fallback budget. router.test.ts:291-309 takes its ceiling from fakeBinding(20), the svc KV test sends one request, no test asserts the service-scope X-RateLimit-Limit, and wrangler-config.test.ts:94 compares the toml against its own copy of 20. Changing the router constant fails no test.
  - Checked: router.ts:125,148; services/rate-limiter.ts:80-96 (single tier, limit=config.maxRequests); tests/wrangler-config.test.ts:94,121-125; router.test.ts:291-309
- Origin: At 8ecb878f the multiplier fed MemoryRateLimiter, which enforced it (services/rate-limiter.ts at main uses `new MemoryRateLimiter()`). 1eaefd63 (PR #229, Sprint 7) moved enforcement to the bindings, which left the constant reporting-only.

## Fix
- Export the multiplier from one module, import it in wrangler-config.test.ts and router.test.ts, and add a service-scope 429 assertion on X-RateLimit-Limit (20 x RATE_LIMIT_REQUESTS). api-worker only, no package publish.
