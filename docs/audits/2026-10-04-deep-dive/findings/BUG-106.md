# BUG-106: tutorial-spotlight.ts: window-only scroll listener and a fixed 100ms measurement leave the spotlight off-target after a container smooth-scroll
**Severity:** LOW · **Type:** Logic · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/tutorial-spotlight.ts:170`

## Evidence
- Reproduction: Tutorial step whose target is within 100px of the viewport edge -> the shadow scroll container smooth-scrolls -> updatePositions runs once at 100ms mid-scroll -> highlight and tooltip stay on the stale rect
- The earlier-audit BUG-086 scroll listener sits on window, but the shell host is height:100vh with overflow:hidden, so tools scroll inside shadow containers (.v4-layout-content-scroll, .v4-tool-main) and window gets no scroll event. A smooth scrollIntoView (:534) is measured once after a fixed 100ms (:264-267), and ResizeObserver does not fire on scroll, so the spotlight and tooltip stay at the mid-scroll rect. The full-screen overlay (:195-202) mostly blocks user scrolling, so the smooth-scroll path is the real repro.
  - Checked: tutorial-spotlight.ts:170-174,257-267,529-539; v4-layout-shell.ts:139-143 (host 100vh overflow hidden), :169-171 (.v4-layout-content-scroll overflow-y:auto); v4-layout.ts:589
- Second, independent check (severity LOW): The mechanism is real, but MEDIUM overstates it.
- **What happens:** the window 'scroll' listener at tutorial-spotlight.ts:170-174 never fires for in-app scrolling. The shell host is height:100vh with overflow:hidden (v4-layout-shell.ts:139-143), and element scroll events do not bubble to window. The positions are measured once, at a fixed 100ms (:264-267), after a smooth scrollIntoView (:534-537). The ResizeObserver (:546-552) fires on observe() and on size changes, but not on scroll, so nothing re-measures once the scroll ends.
- **Why I grade it LOW:** the visible effect is cosmetic, it is narrow, and the tour stays fully usable.
  - The tooltip is clamped to the viewport (:351-352), so Next and Skip always stay reachable.
  - The full-screen fixed overlay leaves no scrollable ancestor, so a user cannot scroll it into the bad state.
  - The bug needs scrollIntoViewIfNeeded to actually scroll. For the default Harmony tour, the first target is the first `.swatch-grid` in the palette drawer's `.drawer-content` (overflow-y:auto, dye-palette-drawer.ts:252-254). By my rough layout estimate it sits about 350-490px down, so a scroll happens only when innerHeight is below roughly 590px (short laptop windows). Step 2 also scrolls, but only after step 1 did.
  - It does not happen with prefers-reduced-motion, where the scroll is instant.
  - The tour runs only when the user picks "Take tour" in the one-time welcome modal.
- Origin: git grep at 8ecb878f finds tutorial-spotlight.ts:170 window 'scroll' listener; git diff 8ecb878f HEAD on the file is empty

## Fix
- Attach scroll listeners to the target's scrollable ancestors, walking across getRootNode().host, and remove them on hide/destroy.
Re-run updatePositions on scrollend, or poll with rAF until the rect settles after scrollIntoView. Add a jsdom test with a scrollable ancestor inside a shadow root.
