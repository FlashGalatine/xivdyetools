# BUG-005: command-trace isUserCondition counts the Universalis client's synthetic 408 timeout as an answered 'rejected' outcome
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/discord-worker/src/services/command-trace.ts:310`

## Evidence
- Reproduction: Universalis or the proxy stalls for 10 s or more during /budget with no stale price cache: the client aborts and throws 408, the outcome is 'rejected', and /stats and AE count it as a success
- isUserCondition (command-trace.ts:310-312) accepts any 4xx except 429. universalis-client.ts:170-172 turns the abort from its own 10 s timer into UniversalisError(408), and workerd's abort rejection is an Error named AbortError (probed). fetchWithCache rethrows that error when no stale entry exists, budget.ts:409 classifies it as 'rejected', and ANSWERED_OUTCOMES (line 71) records the timeout as success.
  - Checked: universalis-client.ts:123-134,170-172; price-cache.ts:220-237 rethrow; budget.ts:409 classifyError; command-trace.ts:71,240; proxy UPSTREAM_TIMEOUT_MS=10_000 (cached-fetch.ts:51) starts after the client's 10 s timer, so the client abort wins on an upstream stall; miniflare probe: aborted service-binding fetch rejects {instanceof Error: true, name: 'AbortError'}
- Second, independent check (severity MEDIUM): Confirmed end to end. The client's own 10 s abort throws UniversalisError(408) (universalis-client.ts:79,123,170-172). fetchPricesBatched does not catch it, and fetchWithCache rethrows it when there is no stale cache (price-cache.ts:220-237). budget.ts:409 marks classifyError(error), and isUserCondition (command-trace.ts:310-312) accepts 408, so the outcome is 'rejected'. ANSWERED_OUTCOMES (line 71) then records success:true (line 240), even though the user is shown budget.errors.apiError (budget.ts:417-420). Severity stays MEDIUM, not LOW. It is telemetry-only, the 'rejected' class still spikes during a stall, and it needs no stale cache entry younger than 15 minutes. But it files an upstream stall under our own payload, inflates the /stats success rate during an outage, and Workers Logs are pinned off, so there is no backup signal.
- Origin: git show 8ecb878f: universalis-client.ts:172 throws 408 and command-trace.ts:310-311 has the identical isUserCondition; git log 8ecb878f..HEAD on budget.ts, services/budget/, command-trace.ts is empty

## Fix
- Classify timeouts as upstream: exclude 408 in isUserCondition, or throw UniversalisError(504/0) on abort. Add a 408 row to command-trace.test.ts:366-373.
