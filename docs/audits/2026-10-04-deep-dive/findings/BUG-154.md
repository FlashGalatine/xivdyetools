# BUG-154: publish-packages.yml Publish loop records FAILED+= and keeps publishing dependents of a failed package
**Severity:** LOW · **Type:** Error handling · **Deploy unit:** root (CI/scripts) · **Covered by test?** no · **Origin:** MAIN · **Other units:** packages/svg, packages/bot-logic (npm consumers)

## Location
- `.github/workflows/publish-packages.yml:157`

## Evidence
- Reproduction: all-modified with core+svg+bot-logic bumped; core publish fails (transient/OIDC) -> svg and bot-logic still published pinning a core version absent from npm -> npm install fails for external consumers
- Loop (155-163) never skips later packages after a failure; svg/bot-logic use workspace:* on core, which pnpm rewrites to core's unpublished local version. release-process.md:56-58 itself says such a consumer fails to install for external users. Self-heals only after core is republished.
  - Checked: publish-packages.yml:155-170; packages/svg/package.json:33 and bot-logic/package.json:37 `workspace:*`; docs/developer-guides/release-process.md:54-58
- Second, independent check (severity LOW): The defect is real. The Publish loop at /c/dev/XIVProjects/xivdyetools/.claude/worktrees/preview-2026-10-04/.github/workflows/publish-packages.yml:155-164 appends a failed package to FAILED (line 161) and carries on to the next package. It never checks whether that next package depends on the one that failed. svg and bot-logic depend on core through `workspace:*`, so a run where core fails can still publish svg and bot-logic pinned to a core version that is not on npm. The loop is byte-identical at main@8ecb878f, so the origin is MAIN, and no test covers the workflow.

I grade it LOW rather than MEDIUM, for five reasons:
1. It only happens at publish time, after Build and Test have already passed for every selected package. The dependency's own `pnpm publish` has to fail mid-run, and it has to be a failure specific to that package, such as one package's trusted-publisher config. A transient network or OIDC fault would usually fail the dependents too.
2. The failure is loud. The job exits 1 with a "Failed to publish core" annotation, so it is never a silent bad release.
3. It fixes itself. Rerunning `all-modified` publishes core, which is still behind npm, and skips svg and bot-logic, which are already at the new version. The pinned core version then exists and the broken range resolves.
4. No first-party app is affected, because every app consumes these packages through `workspace:*`.
5. During the window, an external `npm install` of the new svg or bot-logic fails outright with ETARGET. Nobody gets a silently wrong result.

On the brief's scale that makes it latent and defended elsewhere, so LOW. It is not an edge-path wrong result.
- Origin: git show 8ecb878f:.github/workflows/publish-packages.yml -> FAILED+=("$pkg") at :161, no break/skip

## Fix
- Do not blanket-break (TIER_ORDER puts worker-kit before svg); skip any later package whose workspace: deps include a FAILED one, and in single-package mode verify each workspace dep version exists on npm. Workflow-only, no package publish.
