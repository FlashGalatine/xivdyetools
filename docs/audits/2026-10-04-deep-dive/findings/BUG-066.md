# BUG-066: retention-job.ts runRetentionJob: prunes swallow D1 errors, so a failed sweep reports success with no durable signal
**Severity:** LOW · **Type:** Error handling · **Deploy unit:** apps/presets-api · **Covered by test?** partly · **Origin:** PR-#224 · **Other units:** none

## Location
- `apps/presets-api/src/retention-job.ts:43`

## Evidence
- Reproduction: Persistent D1 error (e.g. table or column drift) at 04:23 UTC -> all three prunes warn and return -> console.log done {fulfilled:3,rejected:0}; nothing persisted, so retention lapses unnoticed
- Every real prune catches its own D1 error and returns void, so `rejected` can never be non-zero and a total failure still logs done {fulfilled:3,rejected:0}. The docblock's 'visible in the prune's own warning' (retention-job.ts:29-31) has no durable channel because observability is pinned off. Graded LOW: the prunes go by age and are idempotent, so a transient D1 failure clears on the next run, and only a persistent failure, which nothing in the current schema produces, would let retention lapse.
  - Checked: retention-job.ts:37-55 allSettled over void prunes; moderation-retention-service.ts:89-90, notification-service.ts:297-298, rate-limit-service.ts:171-172 catch and warn only.; wrangler.toml:65-66 and :129-130 [observability] enabled=false.
- Origin: git show 8ecb878f:apps/presets-api/src/retention-job.ts -> 'exists on disk, but not in 8ecb878f'; added by e34ea70a (pr-delta.txt:25,34 PR #224 +65 -0).

## Fix
- Have each prune return a pruned-count or failed flag (keep swallowing on request paths). runRetentionJob should then throw, or log at error level, when any prune failed, so the invocation records an exception.
No package publish needed; presets-api deploy only.
