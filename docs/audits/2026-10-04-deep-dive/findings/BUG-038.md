# BUG-038: parseIntParam/parseFloatParam accept trailing garbage and exponent forms in query params
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** apps/api-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/api-worker/src/lib/validation.ts:202`

## Evidence
- Reproduction: GET /v1/match/within-distance?limit=1e2 -> limit parsed as 1 -> 1 result instead of 100 (or a 400); ?page=2abc serves page 2
- validation.ts:202 uses parseInt and :244 uses parseFloat with only NaN/finite guards. The repro gave parseIntParam('1e2')=1, '2abc'=2, '50.9'=50, ' 7'=7 and parseFloatParam('10px')=10. Callers are match.ts:78/80, dyes.ts:277-290, harmony.ts:99 and wheels.ts:42. Only the icon id has the CANONICAL guard (chara/router.ts:273).
  - Checked: Repro output: INT "1e2" 1, "2abc" 2, "50.9" 50; FLOAT "10px" 10.; validation.ts:202 `parseInt(value, 10)` / :244 `parseFloat(value)`.; The routes set public s-maxage=86400, so each spelling is its own shared-cache key.
- Origin: git show 8ecb878f:apps/api-worker/src/lib/validation.ts has parseInt(value at 202 and parseFloat(value at 244

## Fix
- Before parsing, reject anything that is not /^-?\d+$/ (ints) or a plain decimal regex (floats). This is an app-local change with no package publish.
