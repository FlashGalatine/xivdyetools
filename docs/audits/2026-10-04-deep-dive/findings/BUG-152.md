# BUG-152: ci.yml workflow-level concurrency ci-${{ github.ref }} + cancel-in-progress: true cancels main-push and nightly-schedule runs against each other
**Severity:** LOW · **Type:** Race · **Deploy unit:** root (CI/scripts) · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `.github/workflows/ci.yml:42`

## Evidence
- Reproduction: Merge 2+ PRs to main within minutes (or push just before 11:17 UTC) -> earlier main runs show cancelled; their changed packages never get a post-merge CI run
- ci.yml:42-44 is a workflow-level group keyed only on ref with cancel-in-progress: true; main pushes and the schedule both resolve to refs/heads/main. A batch merge cancels every run but the last (whose ...[HEAD^] filter only diffs that commit), and an 11:17 schedule run (audit-only, ci/e2e skipped by `if != schedule`) cancels an in-flight push run.
  - Checked: ci.yml:42-44 (concurrency), :98/:134/:339 (`if: github.event_name != 'schedule'`); no workflow_run gating anywhere; git show 8ecb878f:.github/workflows/ci.yml lines 42-44 identical
- Second, independent check (severity LOW): The mechanism is real, but it costs only a redundant post-merge signal, so I'd grade it LOW, not MEDIUM. In .github/workflows/ci.yml:42-44 the concurrency group is `ci-${{ github.ref }}` with `cancel-in-progress: true`. Main pushes and the 11:17 schedule both resolve to refs/heads/main, so a batch merge leaves only the last push run alive, and that run's `...[HEAD^]` filters cover only its own commit. A schedule run can also cancel a push run that is still going. No production result is wrong, though:
- Each PR was already gated by its own pull_request CI (refs/pull/N/merge), and that CI is the real gate.
- No deploy workflow waits on CI. They have their own groups and no workflow_run or needs link to ci.yml, so a cancelled main run blocks and alters nothing.
- Batch merges are already covered by the local preview/integration branch, which runs the gates over the combined tree.
- When a push cancels the nightly run, nothing is lost, because `audit` has no `if` and runs on push too.
- The schedule overlap needs a push run still going at 11:17 UTC (about 07:17 maintainer time), which is rare.
So this is LOW: latent and covered by PR CI. The suggested fix is also incomplete: with `cancel-in-progress: false`, GitHub still keeps only one pending run per group, so merging 3 or more PRs still drops the middle runs. The group key needs `github.event_name` plus `github.sha` (or `run_id`) for push and schedule events.
- Origin: git show 8ecb878f:.github/workflows/ci.yml -> lines 42-44 same group/cancel-in-progress: true

## Fix
- cancel-in-progress: ${{ github.event_name == 'pull_request' }}, or add github.event_name (and sha for push) to the group. No package publish.
