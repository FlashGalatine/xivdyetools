# BUG-057: xivauth.ts roster guard (earlier-audit BUG-051) validates only that the roster is an array; a null element gives a 500, and an empty verified name gives an empty username
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** apps/oauth · **Covered by test?** partly · **Origin:** MAIN · **Other units:** none

## Location
- `apps/oauth/src/handlers/xivauth.ts:342`

## Evidence
- Reproduction: XIVAuth /api/v1/characters returns 200 `[null]` -> POST /auth/xivauth/callback returns 500 'Authentication failed' instead of the degraded 'XIVAuth User <id>' login
- characters = roster when it is an array (line 297), so with [null] the filter throws inside the try and `characters` stays [null]. Then find at :342 throws outside it, giving 500 'Authentication failed'. Reproduced. A verified character with name '' passes `??` and produced a 200 with an empty display name. Latent: it needs the trusted XIVAuth upstream to return malformed data.
  - Checked: xivauth.ts:296-305 (assign before element use), :342-344 (find outside the try; `??` keeps ''); temp repro (deleted): [null] gave 500, [{verified:true,name:''}] gave 200 with an empty name
- Origin: git show 8ecb878f:apps/oauth/src/handlers/xivauth.ts lines 297 and 342-343 are identical; no commits since 8ecb878f touch it

## Fix
- Filter the roster to non-null objects before assigning. Use a verified character's name only when it is a non-empty string, otherwise fall back to 'XIVAuth User <id>'. Extend the earlier-audit BUG-051 it.each with [null] and an empty-name case.
