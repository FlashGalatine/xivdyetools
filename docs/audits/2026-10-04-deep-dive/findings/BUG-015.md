# BUG-015: budget-tool.ts findAlternatives has no run guard; a superseded run overwrites this.rows after a newer run
**Severity:** MEDIUM · **Type:** Race · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/budget-tool.ts:546`

## Evidence
- Reproduction: While the mount-time price fetch is in flight, change target or slider; if the second batch resolves first, the late first run renders the old target's or threshold's ledger under the new target card.
- The target and threshold captured before await fetchPrices are reused after it. A superseded fetch returns an empty Map (market-board-service.ts:359-365), but the continuation still writes this.rows (582-598) and renders. Reordering needs two overlapping uncached batches with different keys, such as the mount fetch plus an early slider tick or selectDye. After the first fetch the consolidated IDs come from cache. Edge path, hence MEDIUM.
  - Checked: budget-tool.ts:546-615 has no generation check; market-board-service.ts:359-365 superseded path; APIService.ts batchKey coalesces only identical uncached sets
- Second, independent check (severity MEDIUM): The race is real, but it is narrower than the finding says. budget-tool.ts:546-606 reads the target and threshold before `await this.fetchPrices` (577) and writes `this.rows` (582-598) afterwards with no generation check. A superseded call still returns normally with an empty Map (market-board-service.ts:359-365), so the stale continuation runs to the end and renders. renderLedger (1393-1435) draws whatever `this.rows` holds under the current `this.targetDye`.

What limits it: cofferDyes() (530-532) always adds all 20 non-consolidated dyes, and custom dyes have a negative itemID, so they are filtered out by shouldFetchPrice (296-301). Each run's market-ID set is therefore those 20 plus whichever of the consolidated IDs 52254/52255/52256 its target and candidates touch. When two runs ask for the same uncached set, APIService.ts:987-1005 shares one promise between them. Both resume in start order, so the newer run writes last and the stale write is never painted.

The reorder only happens when the two runs differ in which consolidated types they touch, or when one run is fully cached and the other is not. Cache writes are synchronous, because the wrapper's `set` updates memory and does not wait for IndexedDB, so no other timing window opens there.

Concrete cases:
- **Mount:** the mount run without a target fetches 20 IDs. An early selectDye of a Type-A dye fetches 21. If the second request returns first, the late mount run captured `target = null` and sets `this.rows = []`, so the new target shows an empty ledger.
- **Two quick picks:** pick T1 (Type C, not yet cached), then quickly T2 (types already cached). T2 resolves almost at once, and T1's late continuation writes T1's rows under T2's card.

The 5-minute API_CACHE_TTL re-opens this window during a long session. No test covers superseded runs (budget-tool.test.ts has no race or superseded case). It needs out-of-order completion or a cache-state change within network latency, so it is an edge path, but the result is a visibly wrong ledger. That fits MEDIUM, not LOW.
- Origin: git diff --stat 8ecb878f HEAD -- budget-tool.ts, market-board-service.ts: empty

## Fix
- const run = ++this.runId at the top; after the await (and in catch/finally), if (run !== this.runId) return; optionally debounce the slider input. Web-app only.
