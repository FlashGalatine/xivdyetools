# BUG-001: swatch-tool setConfig applies ConfigController's full swatch config (default hairColors/SeekerOfTheSun/Female) over tool-local eyeColors/Midlander/Male state
**Severity:** HIGH · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/swatch-tool.ts:466`

## Evidence
- Reproduction: Fresh profile, Swatch on Eye palette: change max results or a display option in the sidebar -> controller.setConfig notifies the full config -> palette switches to Hair, tribe to Seeker/Female, selection nulled, all persisted
- Every hop is traced. The sidebar writes a partial, the controller merges it into stored or default values and broadcasts the whole object, and swatch setConfig treats colorSheet/race/gender as authoritative. Nothing ever writes the tool's colorSheet into the controller.
  - Checked: config-controller.ts:306-334 merges and notifies the full config; config-sidebar.ts:813/873/907 write partials; tool-config-types.ts:489 vs swatch-tool.ts:158-163 defaults; Only writers of colorSheet: swatch-tool.ts:1587/1796/1825 call the tool-local setConfig; subscribe (config-controller.ts:346) does not fire on subscribe, so the flip happens on the next notification
- Second, independent check (severity HIGH): I traced the path from the code and reproduced it with a real ConfigController; the finding holds. On a fresh profile the tool starts from its own DEFAULTS: eyeColors, Midlander, Male (swatch-tool.ts:158-163, 309-331). The controller starts from different defaults: hairColors, SeekerOfTheSun, Female (tool-config-types.ts:488-491). onMount (swatch-tool.ts:360-408) never seeds the tool from getConfig('swatch'). The palette rail, range toggle and slot pick call only the tool's own setConfig (swatch-tool.ts:1587, 1796, 1825), so the controller's colorSheet is never written. On the other side, the sidebar's handleConfigChange (config-sidebar.ts:813) and its display-option and dye-filter fan-outs (873, 907) send partial updates. ConfigController.setConfig (config-controller.ts:306-334) merges each partial into the stored or default config and broadcasts the whole object. The swatch subscriber (swatch-tool.ts:376) passes that object to setConfig, and setConfig treats colorSheet, race and gender as authoritative (450-472). It reloads the colors, sets selectedColor to null and persists everything to the tool's storage keys. No other guard sits on the path: v4-layout's config-change forward only adds a harmless partial, and pinToCharaFile pins only race and gender. Because the rail still never writes to the controller, the flip comes back on every later sidebar change. Existing tests miss it because swatch-tool.test.ts mocks ConfigController with a subscribe that never fires. Severity stays HIGH. Changing max results, a display option, the matching method or a dye filter while on Swatch is an ordinary action, and it silently switches the palette and tribe/gender and drops the selection. The user can recover by clicking the Eye chip, but the next setting change flips it again.
- Origin: git diff 8ecb878f HEAD over swatch-tool.ts, config-controller.ts, config-sidebar.ts, tool-config-types.ts is empty; 8ecb878f:tool-config-types.ts:489-491 has the hairColors/SeekerOfTheSun/Female defaults

## Fix
- Make ConfigController the single owner: seed subrace/gender/colorSheet/maxResults from getConfig('swatch'), route rail/slot picks through ConfigController.setConfig('swatch', {colorSheet}), align the default table with the tool (web-app deploy only)
