# BUG-101: my-submissions-modal.ts: after a successful delete the modal keeps showing the deleted preset and stale stats
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/my-submissions-modal.ts:212`

## Evidence
- Reproduction: Delete -> Confirm -> deleteSuccess toast -> the row and published/awaiting counts are unchanged; Delete again calls the API for the gone preset -> deletePresetFailed toast
- The confirm button runs onConfirm() without awaiting it, then dismisses the confirm (modal-container.ts:347-350). On success the handler only calls onChanged, which reloads the preset-tool lists underneath (preset-tool.ts:1081-1084). The My Submissions rows, stat tiles and subtitle are innerHTML built once (:89-176), so the deleted row stays, and the later dismiss(confirmId) at :216 is a 'Modal not found' no-op.
  - Checked: my-submissions-modal.ts:169-176,206-222; modal-container.ts:345-350; my-submissions-modal.test.ts:110 only counts delete buttons
- Second, independent check (severity LOW): The core defect is real, and its origin is MAIN. After a delete, my-submissions-modal never updates its own content. The rows, stat tiles and subtitle are built once into a detached `content` element (my-submissions-modal.ts:89-176, :229-235). onChanged only reloads the preset-tool lists underneath (v4/preset-tool.ts:1081-1084). The confirm handler in modal-container.ts (around lines 345-351) dismisses the confirm right away without awaiting, so the later dismiss(confirmId) at :216 hits the 'Modal not found' warn path (modal-service.ts:211-212). The finding's repro is partly wrong, though. deletePreset never throws: it returns {success:false} on a non-OK response or a network error (preset-submission-service.ts:493-502). A second Delete on the already-deleted preset therefore shows another deleteSuccess toast, not deletePresetFailed. That false-success path is a separate finding already filed in review-webapp-services.md:28-31. I would grade this one LOW, not MEDIUM. It is display-only staleness in a modal the user just acted on. No data is wrong, the success toast tells the truth, the underlying list is refreshed, closing and reopening the modal shows the correct state, and a repeat delete of a gone row is harmless. That fits the brief's 'cosmetic' band, not a wrong result.
- Origin: file identical at 8ecb878f and HEAD (git diff empty)

## Fix
- On success, remove the row and recompute the tiles, or dismiss and re-open showMySubmissionsModal(onChanged); drop the redundant dismiss(confirmId).
