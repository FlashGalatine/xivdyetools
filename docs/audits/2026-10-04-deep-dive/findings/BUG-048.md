# BUG-048: preferences getUserPreferences swallows read failure as {} and the set/reset writes then overwrite or delete the user's whole prefs blob
**Severity:** LOW · **Type:** Error handling · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/discord-worker/src/services/preferences.ts:138`

## Evidence
- Reproduction: kv.get rejects once, then /preferences set theme:light runs: put({theme}) drops every other pref. A reset of one key under the same failure deletes the whole blob, and both report success.
- The swallow is at preferences.ts:138-142 (claim cited 126): a kv.get rejection or a JSON.parse failure returns {}. setPreferences (281-291) applies the new key to that {} and puts it, replacing the whole blob. resetPreference(key) (333-347) then sees hasPrefs false and kv.delete()s the blob. Both report success. This is a failed read treated as empty, not the earlier-audit BUG-036 concurrency race.
  - Checked: preferences.ts:126-143 (catch -> return {}), 281-291 (put after lenient read), 333-347 (delete when empty); preferences.exhaustive.test.ts:329-335 asserts only that the read returns {}; no write follows
- Second, independent check (severity LOW): The defect is real. getUserPreferences (apps/discord-worker/src/services/preferences.ts:126-143) catches every error and returns {}. setPreferences (:273-288) then applies the new key to that {} and puts it over the whole blob. resetPreference(key) (:333-348) then finds no remaining prefs and kv.delete()s the blob. Both report success. I would grade it LOW rather than MEDIUM, for three reasons. (1) The JSON.parse arm is effectively unreachable: the blob's only writers in this repo use JSON.stringify (services/preferences.ts:285/345/166 and the dyeFilters writers at handlers/commands/preferences.ts:722/786), and a KV value is replaced atomically. (2) The only live trigger is a kv.get that rejects while a kv.put moments later in the same invocation succeeds, which is a partial KV fault. In a general outage the put fails as well and nothing is lost. (3) What is lost is about 16 display and default settings that a user can re-enter with one /preferences set. Since v5 deleted favorites and collections (CHANGELOG:683), no user content lives in this blob. earlier-audit BUG-036 already accepts silent loss of a write to this blob from a far likelier trigger (concurrent writes). So this is a latent edge-path fault with recoverable, low-value data, not a routine edge-path wrong result.
- Origin: git log 8ecb878f..HEAD -- apps/discord-worker/src/services/ is empty; the same code is at 8ecb878f

## Fix
- Add a strict internal read that rethrows on KV or parse failure, and use it in setPreferences and resetPreference so the write aborts and reports an error. Keep the lenient read for command-time lookups.
