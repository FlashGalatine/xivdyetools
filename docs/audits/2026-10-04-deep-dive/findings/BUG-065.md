# BUG-065: presets PATCH /:id re-moderates unchanged text; a failing/unscored verdict re-queues an approved (or resubmits a rejected) preset
**Severity:** LOW · **Type:** Logic · **Deploy unit:** apps/presets-api · **Covered by test?** partly · **Origin:** MAIN

## Location
- `apps/presets-api/src/handlers/presets.ts:656`

## Evidence
- Reproduction: Owner of an approved preset whose stored name a moderator approved after a Perspective flag runs /preset edit name:<same name> tags:x -> moderateContent fails -> status pending, removed from public view, moderator pinged.
- The text_edit reservation and moderateContent are gated on `body.name || body.description`, not on textChanged. When stored text fails or is unscored (moderator-approved-after-flag text, Perspective outage, every call after the key sunset), re-sending it unchanged sets flaggedByThisEdit. ownerEditOutcome then moves an approved or rejected preset to pending and notifies. The existing 'unchanged' test only exercises text that passes moderation.
  - Checked: presets.ts:652-656 textChanged vs `if (body.name || body.description)`; :706-715 flaggedByThisEdit; moderation-service.ts:377-384 unscored -> passed:false; tests/handlers/presets-quotas.test.ts:510-521 uses clean STORED_NAME only
- Origin: git show 8ecb878f:presets.ts:620-624 identical textChanged + `if (body.name || body.description)` gate

## Fix
- Gate reserveDailyEvent('text_edit') and moderateContent on textChanged (skip both when the text equals what is stored), and add the unchanged + failing-verdict test case. presets-api deploy only.
