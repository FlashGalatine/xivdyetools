# BUG-020: gradient-tool calculateInterpolation seeds usedDyeIds with endpoints only, so a free step before a pinned step can match the pinned dye undeduplicated
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/gradient-tool.ts:1809`

## Evidence
- Reproduction: 8 steps, preventDuplicates on, pin step 5 = X: step 4 interpolates toward X's hex; when its closest dye is X, usedDyeIds lacks X, so steps 4 and 5 are both X (step 6 would be deduped)
- The asymmetry is unconditional in the code. Whether the duplicate shows depends on dye geometry, but a step interpolating toward a pinned anchor is the likely case.
  - Checked: gradient-tool.ts:1809 seeds the set; a pinned dye is added only at 1840 when the loop reaches its index; dedupe check at 1888; gradient-tool.test.ts has only a pin-badge label test (544)
- Second, independent check (severity MEDIUM): The finding holds. apps/web-app/src/components/gradient-tool.ts:1809 seeds usedDyeIds with the two endpoint dyes only. A pinned dye joins the set at :1839, and only when the loop reaches that pinned index. So the dedupe check at :1888 lets any free step before a pin match the pinned dye, while free steps after the pin are deduped against it. The pin click handler (:1420-1425) pins the step's current match. Re-anchoring then interpolates the free step before the pin toward exactly that hex, so a duplicate is the usual result. preventDuplicates defaults to true (:143, :251), and no test covers it. I kept MEDIUM rather than raising it: the wrong result is user-visible, but it only appears after the optional pin interaction, and nothing is lost. The origin is MAIN.
- Origin: git diff 8ecb878f HEAD -- apps/web-app/src/components/gradient-tool.ts is empty; 8ecb878f has the same `new Set<number>([this.startDye.id, this.endDye.id])`

## Fix
- Seed usedDyeIds with every pinnedSteps value before the loop (keep the pinned rows exempt from dedupe themselves)
