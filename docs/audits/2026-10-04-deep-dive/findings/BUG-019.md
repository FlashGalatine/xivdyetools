# BUG-019: gradient/swatch loadFromShareUrl applies share settings to tool-local state only; the next ConfigController notification reverts them
**Severity:** MEDIUM · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/gradient-tool.ts:365`

## Evidence
- Reproduction: Open /gradient/?start=..&end=..&steps=12&interpolation=oklch, then toggle any display option -> setConfig('gradient',{displayOptions}) broadcasts stepCount 8 / interpolation hsv -> steps snap to 8, pinnedSteps cleared, colour space reverts; the sidebar shows 8 throughout
- The share-link state never reaches the controller. Any later broadcast carries the controller's stale values, and setConfig applies them.
  - Checked: gradient-tool.ts:365-384 writes this.stepCount/colorSpace/matchingMethod and local StorageService keys only; setConfig 517-545 applies the controller values as authoritative; subscribe (config-controller.ts:346-362) does not fire immediately, so the revert happens on the next notification, not at mount
- Second, independent check (severity MEDIUM): The defect is real, and MEDIUM is the right severity. gradient-tool.ts:365-384 writes the shared steps, interpolation and algo only to the tool's own fields and to the v3_mixer_* StorageService keys. They never reach ConfigController, while mixer-tool does write its share state through ConfigController.getInstance().setConfig('mixer', ...). In V4 the tool's own slider and select are not visible. v4-layout.ts passes the same mainPanel as both leftPanel and rightPanel, and renderRightPanel (gradient-tool.ts:971-973) clears it, so the ConfigSidebar is the only control. Any sidebar change to the gradient config (a display-option toggle at config-sidebar.ts:873, interpolation, matching method or preventDuplicates) calls ConfigController.setConfig, which merges into the controller's stale stored config. It is a real change, so the earlier-audit OPT-008 no-op skip does not apply, and notifyListeners sends the whole config. The tool's subscriber (gradient-tool.ts:434-435) passes it to setConfig at 517-545, which reapplies stepCount 8 and interpolation hsv, clears pinnedSteps and rewrites v3_mixer_steps. Swatch's loadFromShareUrl (swatch-tool.ts:2919+) follows the same local-only pattern for race, gender, algo and limit. No unit or e2e test covers share params against a later controller broadcast. The share-URL tests at gradient-tool.test.ts:748+ assert only the endpoints and the share button. It is not HIGH because it needs an uncommon pair of steps: open a share link with non-default settings, then touch a gradient sidebar control. The damage is a silent revert of view settings, with no data loss.
- Origin: git diff 8ecb878f HEAD -- gradient-tool.ts swatch-tool.ts config-sidebar.ts config-controller.ts is empty; the only setConfig('gradient'|'swatch') writers are config-sidebar.ts:813/873/907 and config-controller.ts:204

## Fix
- After applying share params, write them through ConfigController.getInstance().setConfig('gradient'|'swatch', {...}) so the sidebar and the tool agree
