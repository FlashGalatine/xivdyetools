# BUG-010: validation-service validatePresetDyes accepts repeated dye ids, bypassing the 3-dye floor and dye_signature dedup
**Severity:** MEDIUM · **Type:** Edge case · **Deploy unit:** apps/presets-api · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/presets-api/src/services/validation-service.ts:236`

## Evidence
- Reproduction: POST /presets dyes [1,2,3] then [1,2,3,3] -> signatures '[1,2,3]' vs '[1,2,3,3]' both pass UNIQUE; [7,7,7] accepted as a 3-dye palette
- validatePresetDyes (validation-service.ts:236-256) checks count, integer and range but never uniqueness, so [x,x,x] and [1,2,3,3] get distinct sorted signatures. A real path exists: /preset submit dye1..dye3 can all name the same dye, and a clean result is auto-approved.
  - Checked: preset-service.ts:40 generateDyeSignature sorts but keeps duplicates; discord-worker preset.ts handleSubmitSubcommand collects dye1..dye6 with no dedupe
- Second, independent check (severity MEDIUM): I couldn't refute it, and MEDIUM is the right severity. validatePresetDyes (validation-service.ts:227-256) checks the array length (3-6), that each id is an integer, and that it is a stainID in 1-254. It never checks that the ids are distinct. It is the only dye check on both submit (presets.ts:1413) and edit (presets.ts:1451). generateDyeSignature (preset-service.ts:40) sorts the ids but keeps repeats, so [7,7,7] passes validation and [1,2,3,3] gets a different UNIQUE dye_signature from [1,2,3]. A user can reach this through the bot: /preset submit (discord-worker preset.ts:424-462) collects dye1..dye6 and resolves each name with no dedupe. A preset whose content passes moderation is stored as 'approved' (presets.ts:994), so it goes into the public gallery with no review. The web-app form can't reach this path because it toggles a dye off when picked twice (preset-submission-form.ts:479-482). That makes this a one-client edge path that needs a deliberate or accidental repeat, so it is not HIGH. The rate limit of 10 submissions per day and later moderator hiding limit the damage but don't stop it. It is not LOW because what gets published is wrong: a "3-dye" palette made of one colour, or a near-duplicate that slips past the duplicate check. No test covers repeated ids.
- Origin: git show 8ecb878f:validation-service.ts:200 validatePresetDyes has the same body, with no uniqueness check

## Fix
- Reject when new Set(dyes).size !== dyes.length in validatePresetDyes (covers submit and edit). App-only, no publish.
