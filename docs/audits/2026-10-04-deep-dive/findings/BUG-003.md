# BUG-003: discord-worker's preset webhook (index.ts:402-407) hard-codes kind 'new', so a flagged edit is posted as "New preset pending" with no diff and no Revert button
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/presets-api (payload lacks an edit marker)

## Location
- `apps/discord-worker/src/handlers/commands/preset-notifications.ts:214`
- `apps/discord-worker/src/index.ts:407` — discord-worker /webhooks/preset-submission (index.ts:402) hardcodes kind 'new', so every flagged edit is posted as 'New Preset Pending' with no diff and no Revert, although the payload carries previous_values
- `apps/discord-worker/src/index.ts:407` — Preset webhook hard-codes kind:'new', so web edits get a 'New preset pending' embed with no diff and no Revert
- `apps/discord-worker/src/index.ts:404`

## Evidence
- Reproduction: A web-app text edit of an approved preset goes pending. The moderation embed reads 'New Preset Pending' with Approve/Reject only and no Revert. Reject removes the whole preset instead of restoring the approved text.
- The webhook always builds kind 'new' (index.ts:407), and the payload carries no edit marker (types/preset.ts:48-73), so a presets-api edit notification (presets.ts:847-867) is titled 'New Preset Pending' with no diff and no Revert (preset-notifications.ts:214). The claim overreaches in one place: bot-path edits still get a two-click Revert, because review-message.ts:146-149 offers it on refresh. Web edits get no Revert at all, and Reject on that embed rejects the whole previously approved preset.
- Second, independent check (severity MEDIUM): I could not refute this. When a web edit of an approved preset is flagged (or Perspective is unavailable), presets-api moves the preset to pending, stores the previous_values snapshot and fires the webhook. That payload has no edit marker. discord-worker always builds the embed as kind 'new' (index.ts:407), so it reads 'New Preset Pending' with no diff and only Approve/Reject. The Revert button only appears for kind 'edit' (preset-notifications.ts:214-224). No other path gives moderators Revert. `/preset moderate` only offers pending/approve/reject/stats, and the refresh in review-message.ts:146-149 shows Revert only when a button has already gone stale. If a moderator clicks Reject, prepareStatusUpdate takes the whole previously approved preset out of the public listing instead of restoring the approved text. This is an edge path and it is recoverable, which is why I keep MEDIUM rather than HIGH: Reject leaves previous_values in place (preset-service.ts:457-463) and votes are kept. Origin is MAIN (8ecb878f index.ts:407 is kind 'new'). No test sends a webhook edit expecting kind 'edit'; the only revert-id assertion is a direct builder test.
- Found independently from another slice: presets.ts:846-866 spreads rowToPreset(editedRow) from SELECT * (preset-service.ts:358, :66-76), so previous_values is sent. index.ts:407 sets kind:'new', and the builder (preset-notifications.ts:214) adds Revert only for kind 'edit'. A web-source flagged edit therefore reaches the channel with no Revert path: the moderation-worker /preset command offers approve/reject only (commands/preset.ts:264). A bot edit gets Revert only through the duplicate legacy post (preset.ts:924).
- Found independently from another slice: Real, but moderators can still approve or reject, and the refresh/moderation-worker paths remain, so LOW.
- Found independently from another slice: index.ts:404 hard-codes kind 'new'. presets-api sends the same type:'submission' payload for edits (presets.ts:845-866), and rowToPreset carries previous_values. A flagged web edit therefore posts 'New preset pending' with no diff and no Revert, while a refresh adds Revert back (moderation-worker review-message.ts:146-149). The origin is MAIN, not PR-#227: main already rendered kind 'new'.
- Origin: git show 8ecb878f: index.ts:407 is kind: 'new' and preset-notifications.ts:163-169 emits Revert only for kind 'edit'. presets-api notification payload has no edit field at 8ecb878f either.

## Fix
- Have presets-api add an edit flag to the submission payload (previous_values is already sent); the webhook maps that to kind 'edit' with original. Both payload types are app-local (presets-api notification-service.ts:70, discord-worker types/preset.ts), so no package publish. Pair with BUG-004.
