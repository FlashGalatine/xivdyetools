# BUG-044: harmony.ts and sibling handlers echo the raw colour/dye option into errors.invalidColor embed descriptions with no sanitizeEmbedText or length cap
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** apps/discord-worker · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/discord-worker/src/handlers/commands/harmony.ts:66`

## Evidence
- Reproduction: /harmony color:<~4000+ chars> -> description over 4096 characters, Discord rejects the reply, user sees 'The application did not respond' instead of the invalid-colour error
- errorEmbed (utils/response.ts:128) passes the description through as-is. The translator's interpolate (bot-logic translator.ts:37) escapes nothing. schemas.ts sets max_length only on world/preset options (:698,1024,...). An input of about 4000 characters pushes the description past 4096, so the type-4 reply is rejected. The reply is ephemeral and the user does this to themselves, so LOW.
  - Checked: harmony.ts:60-70; utils/response.ts:128-134; grep max_length in commands/schemas.ts shows only :698,1024,1032,1125,1133,1255,1304,1334
- Origin: git show 8ecb878f:apps/discord-worker/src/handlers/commands/harmony.ts:66 has the identical errors.invalidColor { input: colorInput } echo

## Fix
- Apply sanitizeEmbedText(input, 100) at each invalidColor/dyeNotFound echo, or route them through one helper. Add max_length (~100) to the free-text dye/colour STRING options and a schema test that every non-choice STRING option has one. Changes discord-worker only.
