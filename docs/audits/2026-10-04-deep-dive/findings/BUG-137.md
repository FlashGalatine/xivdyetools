# BUG-137: HarmonySelector.generateHarmonySlots reserves a pinned dye only for later slots under preventDuplicates, so an earlier slot can choose the same dye
**Severity:** LOW · **Type:** State · **Deploy unit:** packages/core · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/web-app harmony-tool (the only pin caller)

## Location
- `packages/core/src/services/dye/HarmonySelector.ts:224`

## Evidence
- Reproduction: preventDuplicates:true, pinned {1 -> X} where X is slot 0's natural pick (e.g. after a matching-method change with a pin kept) -> slot 0 and slot 1 both show X
- `used` starts empty and a pin enters it only when its own slot is reached (:242-258), so an earlier unpinned slot can still pick it. Measured: triadic on Dalamud Red with slot 1 pinned to slot 0's pick gives ['Cactuar Green','Cactuar Green']. The claim's exact path (picking the dye from slot 2's companion list) is not reachable, because those companions already exclude earlier dyes. It is reachable because harmony-tool keeps swappedDyes across method, companion-count, dedup and filter changes: switching cie76->ciede2000 after a pin duplicated in 3 base x type combos.
  - Checked: temp repro (deleted): R02 ['Cactuar Green','Cactuar Green']; R02b hits 3; harmony-tool.ts:360-393 clears swappedDyes only on wheel change (also type/base changes at :1013/:970)
- Second, independent check (severity LOW): The defect is real. At HarmonySelector.ts:224 `used` starts empty, and a pin only enters `used` when the loop reaches its own slot. So an earlier slot left unpinned can still choose the pinned dye, even with preventDuplicates on. It is not reachable from a single UI action: harmony-tool only pins a dye picked from that slot's own companions (onSwapDye at :1524, handleSwapDye at :1688), and under preventDuplicates those companions already leave out every dye an earlier slot holds. My sweep of all 2,750 single-pin cases found 0 duplicates when the config stays the same. It only shows up when a config change leaves the pin in place (:360-393 clears swappedDyes only when the wheel changes) and moves an earlier slot's pick onto the pinned dye. That happened in 3 of 2,750 cases after switching strict matching on, 1 of 2,750 with strict on plus cie76, and 0 when the companion count changed. The pin lives only in memory, and changing the base, the harmony type or the wheel clears it. The result is a visible repeated dye that the user can fix by swapping again, with no data loss. That is an extremely rare, cosmetic edge, so it is LOW, not MEDIUM.
- Origin: git show 8ecb878f:packages/core/src/services/dye/HarmonySelector.ts:224 `const used = new Set<number>();`, same loop; no core commits 8ecb878f..HEAD

## Fix
- When preventDuplicates is on, add every pinned dye's itemID to `used` before the offsets loop, so unpinned slots and companions skip them. Needs a @xivdyetools/core publish, then consumer deploys (web-app).
