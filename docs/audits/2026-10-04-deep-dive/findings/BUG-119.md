# BUG-119: indexeddb-service has no db.onversionchange handler, so an open tab blocks a future DB_VERSION upgrade and the other tab caches initialize()=false
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/web-app/src/services/indexeddb-service.ts:56`

## Evidence
- Reproduction: Tab A is open on v3. Deploy v4 and open tab B: onblocked fires, initialize() resolves false, and tab B never hydrates the persisted price cache.
- onsuccess (:85-89) never installs onversionchange. With a tab open on the old version, a DB_VERSION bump triggers onblocked (:122-125), which resolves false, and initPromise caches that result. get/set self-heal once the blocked open later succeeds, but IndexedDBCacheBackend (api-service-wrapper.ts:85-89, earlier-audit BUG-004 caches its own outcome) never runs loadFromStorage, so that tab's price cache is not hydrated. Latent: it only matters on a future DB_VERSION bump. Caching false after onerror is correct, because those failures are permanent.
  - Checked: indexeddb-service.ts:56-64,85-89,122-125; api-service-wrapper.ts:72-89
- Origin: git diff --stat 8ecb878f HEAD -- apps/web-app/src/services/ is empty; grep finds no onversionchange in indexeddb-service.ts

## Fix
- In onsuccess, set db.onversionchange = () => { db.close(); this.db = null; this.initPromise = null; }. Clearing initPromise on false alone would not restore hydration (earlier-audit BUG-004 latch). Web-app only, no package publish.
