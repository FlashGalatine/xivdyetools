# OPT-009: IndexedDBCacheBackend.loadFromStorage hydrates the price cache with one serial readonly transaction per key
**Impact:** LOW · **Category:** I/O · **Deploy unit:** apps/web-app · **Expected gain:** N serial IDB transactions at boot become a single getAll, so the memory cache is hydrated sooner and fewer early lookups miss it and refetch · **Benchmark:** Seed ~200 keys with fake-indexeddb and count transactions plus time to APIService.isInitialized() before and after · **Other units:** none

## Location
- `apps/web-app/src/services/api-service-wrapper.ts:158`

## Evidence
- Reproduction: Boot with N persisted price keys: N sequential readonly transactions run before the memory cache is fully hydrated
- The cited line 586 is wrong: the file has 266 lines, and the code is at :158-173. It runs keys() and then awaits one get() transaction per key in sequence, although IndexedDBService.getAll already exists. Graded as OPT only. The re-add after clear() is bounded to one in-flight get, that entry is memory-only (IndexedDB stays cleared) and holds public price data, so the FINDING-008 goal still holds. The stale-overwrite race is also bounded, because core's TTL check evicts expired entries on read.
  - Checked: api-service-wrapper.ts:158-173 (serial get loop), :144-149 (clear); indexeddb-service.ts getAll exists
- Origin: git diff --stat 8ecb878f HEAD -- apps/web-app/src/services/ is empty

## Fix
- Use indexedDBService.getAll(STORES.PRICE_CACHE) and skip keys already present in memoryCache. Web-app only, no package publish.
