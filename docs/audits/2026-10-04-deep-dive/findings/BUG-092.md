# BUG-092: gradient-tool.ts loadSelectedDyes drops persisted custom-colour endpoints and moves the remaining dye into the Start slot
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/web-app/src/components/gradient-tool.ts:262`

## Evidence
- Reproduction: Set Start to custom #FF0000 from the palette drawer and End to dye X, then reload /gradient/: Start = X and End is empty
- saveSelectedDyes (301-304) stores d.id, which is the negative synthetic id from makeCustomDye. loadSelectedDyes (266-269) maps those ids through getDyeById, which returns null for them (dyesByIdMap miss), and then filters the nulls out. The array is positional (startDye = selectedDyes[0]), so the surviving end dye moves into Start. Nothing syncs the URL, so a plain reload reads from storage.
  - Checked: gradient-tool.ts:266-269 .map(getDyeById).filter(non-null); 301-304 persists d.id; custom-dye.ts:41 id = -(Date.now()+seq); DyeDatabase.ts:428-430 returns dyesByIdMap.get(id) || null; no replaceState/URL sync in gradient-tool.ts
- Origin: git log 8ecb878f..HEAD -- gradient-tool.ts is empty; loadSelectedDyes and saveSelectedDyes are unchanged since main

## Fix
- Persist the endpoints positionally as {id} or {hex} (custom dyes by hex, rebuilt with makeCustomDye on load), or persist nothing when a slot is custom. Never compact the array.
