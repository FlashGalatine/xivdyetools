# BUG-022: Gradient, Swatch, Mixer and Budget never seed dyeFiltersConfig from the persisted config at mount, so saved dye filters are ignored until the sidebar is touched
**Severity:** MEDIUM · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/mixer-tool.ts:188`
- `apps/web-app/src/components/gradient-tool.ts:246` — GradientTool/SwatchTool never seed dyeFiltersConfig from persisted config at mount

## Evidence
- Reproduction: Enable Exclude metallic, then reload or open Mixer or Budget: metallic dyes appear in Mixer matches and field cells (286, 1276) and in Budget's ledger (568) while the sidebar shows them excluded.
- config-sidebar.ts:893-908 persists dyeFilters into the mixer and budget configs. ConfigController.subscribe (config-controller.ts:346-362) never replays, and neither the Mixer constructor (188-205) nor Budget's constructor or onMount reads dyeFilters, so both start from DEFAULT_DYE_FILTERS. MEDIUM: filters are opt-in.
  - Checked: grep dyeFilters: mixer-tool.ts has only 154/286/935-944/1276, budget-tool.ts only 179/399-407/568, and no mount-time read in either; harmony-tool.ts:339 does read it
- Second, independent check (severity MEDIUM): The defect is real and I agree with MEDIUM. Nothing in either tool's constructor or onMount reads dyeFilters. ConfigController.subscribe only adds a listener and never replays the current value. No other mount-time path pushes the persisted config into the tool. So Mixer and Budget filter against DEFAULT_DYE_FILTERS after a reload or a tool switch, even though the sidebar shows the user's saved filters as on. The filters only take effect once one is toggled again. It stays MEDIUM, not HIGH, because a user has to turn a filter on before this can happen. The same gap also exists in gradient-tool.ts, which strengthens the finding rather than weakening it.
- Reproduction: Toggle 'exclude metallic' in sidebar (persisted to gradient/swatch via config-sidebar.ts:907), reload, open Gradient and pick endpoints -> middle steps (:1859-1894) still match metallic dyes; Swatch matches (:2807-2818) likewise.
- Gradient ctor (gradient-tool.ts:245-251) seeds displayOptions/matchingMethod/preventDuplicates from getConfig('gradient') but never dyeFilters; swatch-tool.ts never reads getConfig('swatch') at all (only 'market' :392). subscribe() (config-controller.ts:346-361) fires no initial callback and v4-layout.ts:192 forwards only {[key]:value}, so persisted filters are ignored until the next sidebar toggle.
  - Checked: gradient-tool.ts:175 field default, :245-251 ctor (no dyeFilters), :434 subscribe only; swatch-tool.ts:246, :374-392; config-controller.ts:346-361 subscribe has no initial notify; harmony-tool.ts:339 shows the correct seed
- Second, independent check (severity MEDIUM): I could not refute this. The defect happens as described. In gradient-tool.ts the field starts at DEFAULT_DYE_FILTERS (line 175), and the constructor (lines 245-251) reads getConfig('gradient') but copies only displayOptions, matchingMethod and preventDuplicates from it, never dyeFilters. swatch-tool.ts never calls getConfig('swatch') at all. The only call is getConfig('market') at line 392, and the fields at lines 243/245/246 keep their hard-coded defaults. ConfigController.subscribe (services/config-controller.ts:346-361) only registers the listener and never calls it with the current value. No other path seeds the value at mount either. The sidebar's config-change events (config-sidebar.ts:817/878/912) fire only on user toggles. The v4-layout.ts:192 forward passes a key like 'dyeFilters.excludeMetallic', which setConfig ignores, because it only acts on config.dyeFilters. ConfigController's onCharaSession calls setConfig('swatch', {}), which notifies listeners only when a .chara load changes something. So after a reload, the sidebar shows the persisted filter as checked (loadConfigsFromController, line 757), while Gradient's middle-step matching (lines 1859-1894) and Swatch's findMatchingDyes (lines 2807-2818) run with no filters. MEDIUM fits: the result is wrong but visible only to users who turned on a filter, which is opt-in and not the common path. No test covers mount seeding; the only swatch test calls setConfig directly.
- Origin: git diff --stat 8ecb878f HEAD -- mixer-tool.ts, budget-tool.ts, config-controller.ts, config-sidebar.ts: empty

## Fix
- Seed this.dyeFiltersConfig from ConfigController.getConfig('mixer'|'budget').dyeFilters in each constructor, before the first match or findAlternatives. Web-app only.
- In gradient and swatch constructors seed this.dyeFiltersConfig = cfg.dyeFilters ?? {...DEFAULT_DYE_FILTERS} (harmony-tool.ts:339 model); fix together with BUG-022 (mixer/budget). Swatch also ignores persisted matchingMethod/displayOptions at mount — seed those too. Web-app only, no package publish.
