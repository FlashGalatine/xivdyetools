# OPT-003: preset.ts favorite list fans out one getPreset per favourite (up to 50)
**Impact:** LOW · **Category:** I/O · **Deploy unit:** apps/discord-worker · **Expected gain:** Up to 49 fewer service-binding subrequests and D1 reads per /preset favorite list. · **Benchmark:** Count presetApi.getPreset / PRESETS_API.fetch calls for a 50-favourite list in preset.test.ts. · **Other units:** apps/presets-api (would need a batch-by-ids endpoint)

## Location
- `apps/discord-worker/src/handlers/commands/preset.ts:1380`

## Evidence
- Reproduction: A user with 50 favourites runs /preset favorite list: 50 parallel service-binding calls.
- preset.ts:1380-1382 makes one presets-api getPreset call per favourite, up to MAX_PRESET_FAVORITES = 50 (preset-favorites.ts:34), via Promise.all. That is up to 50 service-binding subrequests and 50 D1 reads per list. The work runs after the deferred ack (:1358), and getPreset sends no user id, so presets-api's per-user limiter never fires. Pure I/O cost, no correctness impact.
- Origin: git show 8ecb878f:apps/discord-worker/src/handlers/commands/preset.ts:1381 has the same ids.map(getPreset).

## Fix
- Add GET /presets?ids= (batch) to presets-api and use it here. No package publish; two app deploys, presets-api first.

OPEN — needs a presets-api batch lookup (`GET /api/v1/presets?ids=`, approved-only, capped at 50) deployed first; recorded in Sprint 9 (PR #257).
