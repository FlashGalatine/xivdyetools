# BUG-117: CollectionService.initialize re-enters and overflows the stack when a migration save fails
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/web-app/src/services/collection-service.ts:190`

## Evidence
- Reproduction: localStorage quota full + stored favourites/collections needing migration (4.x ids or version!=2.0.0) -> RangeError on first CollectionService call, favourites/collections unusable
- Reproduced with a temp test (deleted): stored collections at version 1.0.0 plus StorageService.setItem returning false makes getCollections() throw RangeError. initialized is set only after loadCollections, and save->notify->getCollections->initialize re-reads the unmigrated data each time.
  - Checked: collection-service.ts:192-197 flag after loads; :452-468 save always notifies; :1051-1062 notify calls getFavorites/getCollections -> initialize
- Second, independent check (severity LOW): The recursion is real, but the condition that triggers it practically cannot happen. In collection-service.ts:189-198, initialize() sets `initialized` only after loadFavorites/loadCollections. A migration save (:452-468) always notifies listeners, the notify functions (:1051-1062) call getX, and getX calls initialize() again, which re-reads storage. If the write did not stick, the data still needs migrating and the loop never ends. In practice the trigger is close to impossible. StorageService.getItem returns null whenever isAvailable() (storage-service.ts:47-60) fails its own probe write, so the loop needs localStorage that passes that small test write but rejects the migration write. On a 5 MB origin the app writes only small settings plus capped favorites (40) and collections (50 x 20 dyes). The favourites migration makes the data smaller, since stainIDs are shorter than legacy itemIDs. Only 4.x collections with few dyes grow, by about 17 bytes for the added `kind` field, and only on a one-time migration from before 5.0 (2026-08-16). The data stays in storage, so this is a hard failure for the session only, with no data loss. Latent, so LOW, not MEDIUM.
- Origin: git show 8ecb878f:apps/web-app/src/services/collection-service.ts has the same flag at :197; no PR commit touches the file

## Fix
- Set initialized=true before loadFavorites/loadCollections, or suppress listener notification while initializing; web-app only.
