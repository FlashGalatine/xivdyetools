# BUG-116: chara-resolve-service resolveCharaEquipment sends unbounded model lanes/glasses id; one lane >0xffff 400s the whole resolve and the Reader reports an outage
**Severity:** LOW · **Type:** Edge case · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN · **Other units:** packages/core (fix in web-app needs no publish)

## Location
- `apps/web-app/src/services/chara-resolve-service.ts:127`
- `packages/core/src/services/chara/chara-parser.ts:498` — chara-parser readModelLane: an out-of-range lane (>65535) sinks the whole /v1/chara/resolve batch
- `packages/core/src/services/chara/chara-parser.ts:498` — chara-parser readModelLane/readGlassesId accept values > 0xffff, so api-worker rejects the whole resolve batch with a 400

## Evidence
- Reproduction: .chara with Body.ModelBase 70000 (other slots valid) -> POST 400 'gear[i].base must be an integer between 0 and 65535' -> all piece names, twins and verdict lost, note blames availability.
- core readModelLane/readGlassesId accept any finite >0 and floor (chara-parser.ts:498-513); api-worker lane() rejects >LANE_MAX 0xffff for the whole body with 400 (router.ts:42,63-75,133-146); client maps any !ok to CharaResolveUnavailableError (chara-resolve-service.ts:156-161) -> resolveState 'unavailable' (glamour-block.ts:370-371) -> 'Item names unavailable' note (en.json:1269) for every piece. Only hand-edited/corrupt files (game lanes are uint16), so LOW.
  - Checked: packages/core/src/services/chara/chara-parser.ts:498-513; apps/api-worker/src/chara/router.ts:42,63-75; apps/web-app/src/services/chara-resolve-service.ts:127-161
- Found independently from another slice: readModelLane (chara-parser.ts:498) floors any positive finite value with no upper bound; api-worker router.ts:73 400s the whole body on any lane > LANE_MAX, and chara-resolve-service.ts:147 turns any non-ok into CharaResolveUnavailableError, so every piece in the file loses its name.
- Found independently from another slice: Real: a temporary repro showed parseCharaFile keeps Body.ModelBase 70000 and GlassesId 99999. api-worker's lane() and glasses check then 400 the whole batch, and glamour-block shows 'Item names unavailable' for every piece (dyes intact). Graded LOW, not MEDIUM: game lanes are uint16, so only a hand-edited or corrupt file can hit this; it degrades gracefully; the key-collision half does not matter (api-worker validates before charaModelKey, and web-app modelHash is keyed per slot).
- Origin: git grep 8ecb878f: router.ts:42 LANE_MAX = 0xffff, chara-parser.ts:498/508 readModelLane/readGlassesId present; no PR commit touches parser/resolve-service/router (git log 8ecb878f..HEAD only 3daa83fd copy change in glamour files)

## Fix
- Web-app only (no publish): drop gear entries/glasses outside 1..0xffff before fetch, or map a 400 to a file-problem note like the bot does. Alternatively clamp in core readModelLane/readGlassesId — needs a @xivdyetools/core publish, then consumer deploys (web-app, discord-worker).
