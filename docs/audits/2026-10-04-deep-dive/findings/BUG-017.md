# BUG-017: collection-manager-modal.ts: creating from the manager never refreshes the manager list, count or create-limit state
**Severity:** MEDIUM · **Type:** State · **Deploy unit:** apps/web-app · **Covered by test?** no · **Origin:** MAIN

## Location
- `apps/web-app/src/components/collection-manager-modal.ts:69`

## Evidence
- Reproduction: Open manager -> New collection -> Create -> 'created' toast, manager still shows old list/empty state; at the limit the still-enabled button leads to a palette.saveFailed toast
- The manager's New collection button calls showCreateCollectionDialog() with no callback (:69). On create, the dialog dismisses only itself (:328). The manager content is static DOM built once (:20-113) with no CollectionService subscription, so the list, the count and createBtn.disabled stay stale until the modal is reopened.
  - Checked: collection-manager-modal.ts:64-71, 101-106 (other paths re-open), 325-331; collection-manager-modal.test.ts:149-163 only calls the dialog directly
- Second, independent check (severity MEDIUM): I could not refute this. collection-manager-modal.ts:68-70 calls showCreateCollectionDialog() with no callback. On a successful create, :326-331 only runs ModalService.dismissTop(), which closes the create dialog that sits on top of the manager. The manager is a detached content element built once at :20-113. It has no subscribeCollections listener, and the modal container keeps the same element, so the count (:32-37), the list or empty state (:77-111) and createBtn.disabled (:67) all stay stale. By contrast, edit and delete (:102-106) and import (:591-592) dismiss the manager and reopen it.

The path is common, not hypothetical. Every DyeSelector in the harmony, accessibility, comparison, gradient and mixer tools passes showFavorites: true, and that renders the Manage Collections button (dye-selector.ts:543-553) that opens this modal. No test covers it: the test file (__tests__/collection-manager-modal.test.ts:151, :166) only calls showCreateCollectionDialog directly and never clicks the manager's own New collection button.

On severity, I considered LOW. Nothing is lost: the collection persists, a success toast shows, and closing and reopening the manager fixes the view. I kept MEDIUM because the stale list invites a retry. A second create with the same name is rejected as a duplicate (collection-service.ts:633-636) and shows a generic palette.saveFailed toast. At the 50-collection limit, the button stays enabled and shows the same misleading error (:639-641). The visible result is wrong and confusing on a normal flow, but the data is fine, so HIGH is too much.
- Origin: git grep 8ecb878f: collection-manager-modal.ts:69 'showCreateCollectionDialog();'; no diff 8ecb878f..HEAD

## Fix
- Pass a callback that does ModalService.dismissTop(); showCollectionManagerModal(); like the edit/delete/import paths do (the dialog has already dismissed itself).
