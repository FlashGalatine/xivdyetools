# BUG-007: apps/oauth/src/index.ts /auth/* limiter keys and tiers on the raw percent-encoded pathname, while Hono routes on the decoded path
**Severity:** MEDIUM · **Type:** Logic · **Deploy unit:** apps/oauth · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/oauth/src/index.ts:184`
- `apps/oauth/src/index.ts:184` — oauth /auth/* rate limiter keys and tiers on the raw percent-encoded pathname while Hono routes on the decoded path

## Evidence
- Reproduction: 25x POST /auth/%63allback (CF-Connecting-IP fixed) -> 25x 400 from the callback handler with limit 30, no 429; the same on /auth/callback returns 429 from request 21
- Line 184 is `new URL(c.req.url).pathname` (raw). hono 4.13.9 getPath decodeURIs, so /auth/%63allback still routes to the callback handler, but getOAuthLimit's startsWith misses and returns the default 30/min, and every spelling gets its own bucket. Reproduced via app.fetch: 25 POSTs to /auth/%63allback all got 400 'Missing code' with X-RateLimit-Limit 30 and no 429. The literal path returned 429 from request 21. Caveat: Cloudflare zone URL normalization could decode %63 before the Worker sees it. That setting is not in the repo, so the grade stays MEDIUM, not HIGH.
  - Checked: index.ts:184 + worker-kit presets/configs.ts:45-51 (startsWith) + node_modules/hono/dist/utils/url.js:68-79 (tryDecodeURI); temp repro (deleted) printed limit 30 / no 429
- Second, independent check (severity MEDIUM): The defect is real. It was already on MAIN at 8ecb878f and no test covers it. In C:/dev/XIVProjects/xivdyetools/.claude/worktrees/preview-2026-10-04/apps/oauth/src/index.ts:184 the limiter takes `new URL(c.req.url).pathname`, which stays percent-encoded. That raw path picks the tier in getOAuthLimit (packages/worker-kit/src/rate-limiter/presets/configs.ts:45-51, a startsWith match) and is also part of the bucket key `${ip}:${path}` in apps/oauth/src/services/rate-limit.ts. Hono 4.13.9 routes on the decoded path instead (node_modules/hono/dist/utils/url.js getPath calls tryDecodeURI), so every spelling of the same route reaches the same handler but counts against its own bucket.

Severity stays MEDIUM, not higher, for three reasons:
(1) The real problem is the bucket split, not the tier. A wrong tier can even be stricter: /auth/xivauth/%63allback matches the '/auth/xivauth' prefix and gets 10/min instead of 20.
(2) A per-IP limit can already be beaten by rotating IPs. The POST callback also needs a validly signed state with a matching PKCE challenge (FINDING-012) before Discord is called, so the bypass does not let anyone guess codes or skip auth. What it allows is unthrottled traffic from one IP, which is load on Discord's token endpoint and an operational risk.
(3) Whether the production zone decodes %63 before the Worker sees it ("Normalize URLs to origin") is not recorded in the repo. Cloudflare's own rate-limiting docs warn that different path spellings can reach the origin without matching a rule.

Neither point refutes the defect. Both argue against raising it above MEDIUM.
- Found independently from another slice: Real in the Worker: each encoded spelling gets its own 30/min bucket and skips the 10/20 tiers. Whether production request.url arrives un-decoded on the auth.xivdyetools.app custom domain depends on zone URL-normalization settings the repo cannot show; kept at MEDIUM as an operational risk.
- Origin: git show 8ecb878f:apps/oauth/src/index.ts line 184 has the same `new URL(c.req.url).pathname`; git log 8ecb878f..HEAD shows no change to index.ts or services/rate-limit.ts

## Fix
- Key and tier the limiter on c.req.path (the decoded path Hono routes on). Add an app-level test that posts /auth/%63allback past 20 requests and expects a 429. App-only change, no package publish.
