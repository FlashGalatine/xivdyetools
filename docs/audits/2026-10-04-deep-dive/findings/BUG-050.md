# BUG-050: preset-moderation.ts processApproval / preset-rejection.ts processRejection: success embed spreads a prior 'Error' field
**Severity:** LOW · **Type:** State · **Deploy unit:** apps/moderation-worker · **Covered by test?** no · **Origin:** MAIN · **Other units:** none

## Location
- `apps/moderation-worker/src/handlers/buttons/preset-moderation.ts:217`

## Evidence
- Reproduction: Approve hits a presets-api 5xx, so the message gains 'Error: Failed to approve'. The retry succeeds, and the 'Preset Approved' embed still shows the Error field. Each further failure adds one more field.
- Failure paths (preset-moderation.ts:252-271, ban guard :187-202; preset-rejection.ts:195-214) append an 'Error' field and pass no `components`, so the buttons stay live. The success edit at :216-219 (and preset-rejection.ts:157-161, not :521) spreads `originalEmbed.fields`, so the Error field survives under 'Preset Approved'.
  - Checked: preset-moderation.ts:216-219 vs :259-266; preset-rejection.ts:157-161 vs :202-209; git show 8ecb878f:.../preset-moderation.ts lines 150/188 have the same spread
- Origin: git show 8ecb878f:apps/moderation-worker/src/handlers/buttons/preset-moderation.ts:150 spreads originalEmbed.fields into the 'Approved by' embed; :188 appends Error with no components

## Fix
- Filter out fields named 'Error' before spreading in the success embeds (approve, reject, revert). On a repeat failure, replace the Error field rather than appending another.
