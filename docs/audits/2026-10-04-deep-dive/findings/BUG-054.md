**Severity:** LOW · **Type:** Error handling · **Deploy unit:** apps/moderation-worker · **Covered by test?** no · **Origin:** PR-#225 · **Other units:** apps/presets-api (GET /moderation/:presetId added in 2.4.0, moderation.ts:541)

## Evidence
- Reproduction: mw 1.8.0 live against presets-api 2.3.x (rollback or misordered deploy): legacy/stale click -> GET /api/v1/moderation/<id> route 404 -> 'That preset no longer exists', components: [] ; /preset moderate approve -> 'Preset not found'.
- Real code gap but defended elsewhere: getModerationPreset (preset-api.ts ~404, not :357 which is getPreset) maps any 404, incl. 2.3.x route 404 (main index.ts:259), to null -> review-message.ts:171 strips buttons; mw CHANGELOG:10-11 does order the deploy (after presets-api 2.4.0), so only a misordered deploy or presets-api rollback hits it.
  - Checked: git show 8ecb878f:apps/presets-api/src/handlers/moderation.ts has no GET '/:presetId'; review-message.ts:167-186; mw CHANGELOG.md:10-11 'Deploy right after presets-api 2.4.0'.
- Origin: pr-delta.txt PR #225 changes apps/moderation-worker/src/services/preset-api.ts (+94 -9); getModerationPreset absent at 8ecb878f.

- Return null only when the 404 body is the notFoundResponse 'Preset not found'; treat other 404s as errors that keep the buttons. Optionally note the rollback consequence in the mw changelog. No package publish.
