# BUG-034: input-resolution.ts resolveColorInput: all-digit 6-char hex without '#' (000000, 333333, 123456) is read as a dye id and returns null
**Severity:** MEDIUM · **Type:** Edge case · **Deploy unit:** packages/bot-logic · **Covered by test?** no · **Origin:** MAIN · **Other units:** apps/discord-worker (gradient, mixer-v4, harmony, contrast, accessibility, comparison, extractor handlers), apps/stoat-worker dye-resolver

## Location
- `packages/bot-logic/src/input-resolution.ts:210`

## Evidence
- Reproduction: resolveColorInput('000000') -> null (ran in a temp repro: '000000','333333','123456' all null, '#000000' -> {hex:'#000000'})
- isBareNumber (l.49) wins before isValidHex; parseDyeIdInput gives null for 0 and for >48227 (max legacyItemID), so /gradient, /mixer, /harmony, /contrast, /accessibility reply invalidColor; resolveDyeInput accepts the same input.
  - Checked: input-resolution.ts:39-51,210-214 vs 295-307; dyes.json legacyItemID range 5729..48227; CHANGELOG.md:439 names only the 3-digit shorthand as the accepted ambiguity
- Second, independent check (severity MEDIUM): The defect is real, so the finding stands. In resolveColorInput, isBareNumber (input-resolution.ts:49-51) runs at :210 before the isValidHex branch at :217. For '000000', parseDyeIdInput (:39-46) gets n=0 and returns null. For '123456' or '333333', n is at least 5729, so it calls getDyeById, which returns null because the highest legacyItemID in dyes.json is 48227. The function then returns null at :212 and never reaches the hex check. Its own docstring (:190) says it accepts 'FF0000' without '#', and isValidHex says the '#' is optional. Before 2026-08-29 these inputs resolved to the hex colour, so this is a regression from that change. The CHANGELOG entry for it names only the 3-digit shorthand as an accepted ambiguity. A hex with a leading zero that happens to equal a legacy item id has a quieter failure: '013114' resolves to the dye Pure White instead of the colour #013114, with no error. Nothing upstream catches it. The discord-worker handlers (gradient.ts:55/68, mixer-v4.ts:51/59, harmony.ts:60, contrast.ts:56, accessibility.ts:64, comparison.ts:21, extractor.ts:90) pass the raw option value straight in and reply errors.invalidColor. Stoat-worker partly recovers: its fallback to resolveDyeInput (:306) returns the closest dye instead of the exact hex. No test covers it. input-resolution.test.ts tests only '#123456' (:162) and alphanumeric 'FF0000' (:150), and nothing grep finds anywhere tests an all-digit 6-char hex without '#'. Two points argue against going higher. The option hints in schemas.ts:161/302/382/389 show the '#' form, and the usual failure is a visible invalidColor error that a retry with '#' fixes. Still, it is a wrong result for valid input on an edge path. It is not cosmetic, latent, or defended elsewhere, so MEDIUM is correct and HIGH is not warranted.
- Origin: git show 8ecb878f:packages/bot-logic/src/input-resolution.ts:210 has the same isBareNumber branch; PRs touch only bot-logic locale JSON

## Fix
- In the bare-number branch, when parseDyeIdInput returns null and the input is 6 digits (isValidHex), fall through to the hex branch. Needs a @xivdyetools/bot-logic publish, then discord-worker/stoat-worker deploys.
