# BUG-009: opening a second modal strips the first one's listeners, leaving it unclosable
**Severity:** HIGH · **Type:** State / lifecycle · **Deploy unit:** `web-app` · **Covered by test?** no

## Location
- `apps/web-app/src/components/base-component.ts:156-159` — `update()` calls `unbindAllEvents()` (which clears the whole listener map, `:615-623`), then `render()`, then `bindEvents()`.
- `apps/web-app/src/components/modal-container.ts:486-498` — `render()` is incremental (WEB-PERF-002): a modal already in `renderedModalIds` is **skipped**, so `createModalElement()` never runs for it again.
- `apps/web-app/src/components/modal-container.ts:389,447,306,265-282` — the close button, backdrop, footer buttons and drag handlers are all bound inside `createModalElement()`.
- `apps/web-app/src/components/modal-container.ts:538-539` — `bindEvents()` re-binds only the document `keydown` handler.

## Evidence
- Every stack change goes through `update()`, so the listener map is cleared for all modals; only newly created ones get listeners back. The already-rendered modal underneath keeps its DOM but loses its ✕, its backdrop click, its footer Cancel/Confirm and its drag handles.
- Reproduction: open any modal, open a second on top, dismiss the second. The first is now inert to the mouse. `Escape` still works, because the document keydown is the one listener `bindEvents()` restores — which is why the failure reads as "the buttons stopped working" rather than "the modal is frozen".
- Worst case is a confirmation dialog raised under a stack: its Confirm and Cancel are both dead, and a `showConfirm` that the user cannot answer blocks the flow that awaited it.
- The codebase already knows this hazard in the same class: `toast-container.ts:208` carries the comment "Must be re-added here since `unbindAllEvents()` is called during `update()`", and `dye-selector.ts:533` reasons about the same lifecycle. `modal-container` is the incremental renderer that did not get the same treatment.

## Fix
- Rebind the surviving modals after an incremental render: either re-attach listeners for every entry in `renderedModalIds` that was skipped, or move the per-modal bindings into `bindEvents()` so the base class's unbind/rebind cycle covers them.
- Add a test that opens two modals, dismisses the top one, and asserts a click on the remaining modal's close button dismisses it — the current suite never exercises a stack across an `update()`.
