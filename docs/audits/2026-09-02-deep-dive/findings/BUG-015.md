# BUG-015: a one-dye share link is parsed as a number, so single-dye Comparison and Accessibility links open empty
**Severity:** HIGH · **Type:** Edge case / type coercion · **Deploy unit:** `web-app` · **Covered by test?** no — found independently by two reviewers

## Location
- `apps/web-app/src/services/share-service.ts:399-403` — `parseUrl` tries `parseFloat(value)` first and, when `String(numValue) === value`, stores a **number**. The comma-separated array branch at `:417` is only reached when the value contains a comma.
- `apps/web-app/src/components/v4/preset-detail.ts:853,863` — the producer serialises a 1-element id array as the bare `dyes=45`.
- Consumers gate on `Array.isArray(...)` (`comparison-tool.ts:2480`, `accessibility-tool.ts:2041` region), so a number is silently ignored.

## Evidence
- `?dyes=45,102` round-trips correctly as `[45, 102]`; `?dyes=45` becomes the number `45`, fails the `Array.isArray` gate, and the tool falls back to whatever state the recipient already had. The link therefore appears to work — the page loads, the tool renders — while showing the wrong dyes, which is worse than an error.
- The asymmetry is entirely in the arity: the same producer, the same consumer, the same grammar, correct for two or more dyes and broken for exactly one.
- Two reviewers reached this independently from opposite ends (the service and the v4 producer), which is why it is filed at HIGH despite the narrow trigger.

## Fix
- Make the array-ness of a param a property of the key, not of the value: normalise the known id-list params (`dyes`, and any sibling list param) to an array in `parseUrl` regardless of element count, or have the producer always emit a trailing-comma-free array form the parser recognises.
- Add a round-trip test over 1, 2 and 3 ids for every list-valued share param. The current tests only exercise the multi-element case.
- `share-service.ts:407` and `:417` carry two neighbouring coercion defects worth fixing in the same pass: the `'1'`/`'0'` boolean branch is unreachable because those parse as numbers first, and an all-leading-digit hex like `012345` is mangled by `parseFloat`.
