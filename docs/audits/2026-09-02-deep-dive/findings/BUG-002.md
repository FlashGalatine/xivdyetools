# BUG-002: pre-5.0 shared links (`/matcher`, `/character`) get the generic site card, because the rename is client-side only
**Severity:** LOW · **Type:** Logic / contract drift · **Deploy unit:** `web-app` (fix), `og-worker` (affected surface) · **Covered by test?** no

## Location
- `apps/web-app/src/services/router-service.ts:83-84` — `LEGACY_PATHS`: `'/matcher' → 'extractor'`, `'/character' → 'swatch'`. The rewrite happens in the browser, after JavaScript runs.
- `apps/web-app/public/_redirects:3` — `/* /index.html 200`. Every unmatched path is answered with the SPA shell under its original URL; nothing is redirected at the edge.
- `apps/og-worker/wrangler.toml:67-77` — the nine production route patterns are the *new* names only; there is no `/matcher/*` or `/character/*` pattern.

## Evidence
- A crawler fetching `https://xivdyetools.app/matcher?dye=…` is not routed to og-worker (no matching pattern), falls through to Pages, and receives `index.html` with the static site-root card — not an extractor card. Crawlers do not run the client-side router, so they never see `/extractor`.
- `apps/web-app/functions/_middleware.ts:21` shows the codebase already has the mechanism (a 301) and uses it for the retired `projectgalatine.com` apex, but not for the renamed tool paths.
- These are the 4.x tool names, so the affected links are exactly the ones already posted in Discord and social history before the 5.0 rename — the population that cannot be re-shared.

## Fix
- Add `/matcher` and `/character` to the 301 map in `apps/web-app/functions/_middleware.ts`, pointing at `/extractor` and `/swatch` with the query string preserved. The crawler then follows the redirect to a path og-worker does route, and the human gets a real redirect instead of a flash of the wrong URL.
- One `web-app` deploy; no og-worker change needed. Guard it with a test asserting a 301 and the preserved query for both legacy paths.
