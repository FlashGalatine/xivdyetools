# BUG-008: `extractAndMatchPalette` matches with the requested method but always reports RGB distance
**Severity:** MEDIUM · **Type:** Logic / API contract · **Deploy unit:** `@xivdyetools/core` · **Covered by test?** no

## Location
- `packages/core/src/services/PaletteService.ts:456-463` — the match is chosen with `options.matchingMethod`, then `const distance = rgbDistance(ex.color, matchedDye.rgb);` is computed unconditionally and returned as the `PaletteMatch.distance`.

## Evidence
- The function honours `matchingMethod` for *selection* and ignores it for *reporting*, so the returned distance is on a different scale (RGB Euclidean, 0–441.67) from the metric that picked the winner. A caller has no way to tell from the value which metric it is on.
- Consumers treat it as a perceptual delta: the web-app's auto-extract path renders it through the result card's ΔE2000 bands ([[BUG-007]] covers the tool-side half of the same class).
- No test asserts the reported `distance` against the requested method, so the mismatch is invisible to the suite.

## Fix
- Report the distance with the same metric that chose the match — `getDistanceForMethod(hex, matchedDye.hex, options.matchingMethod)` — or return both values under distinct names so callers cannot confuse them.
- Add a test that requests `ciede2000` and asserts the reported distance equals an independently computed ΔE2000.
- Needs a `@xivdyetools/core` publish before consumers pick it up; ships naturally with [[BUG-006]].
