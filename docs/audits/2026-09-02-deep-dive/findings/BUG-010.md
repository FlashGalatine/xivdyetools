# BUG-010: `/preset moderate action:stats` prints "undefined" in all four counters
**Severity:** HIGH · **Type:** Logic / cross-service field-name drift · **Deploy unit:** `moderation-worker` · **Covered by test?** no — the test mocks the field names the client expects, not the ones the API sends

## Location
- `apps/moderation-worker/src/handlers/commands/preset.ts:321-324` — reads `stats.pending_count`, `stats.approved_count`, `stats.rejected_count`, `stats.flagged_count`.
- `apps/presets-api/src/handlers/moderation.ts:297-301` — the SQL aliases those columns `pending`, `approved`, `rejected`, `flagged` (plus `actions_last_week`), and `:306` returns them unwrapped as `{ stats }`.

## Evidence
- No `*_count` key exists anywhere in the response, so all four embed fields evaluate `String(undefined)` and the moderator sees:
  ```
  🟡 Pending  undefined     🟢 Approved undefined
  🔴 Rejected undefined     🟠 Flagged  undefined
  ```
- The suite cannot see it: `apps/moderation-worker/src/handlers/commands/preset.test.ts:876` builds the mock response with the `_count` names the handler reads, so the mock agrees with the client and both disagree with the server.
- This is the moderation queue's only summary view, and it is the shape a moderator checks before working the backlog.

## Fix
- Read the four names presets-api actually returns, and surface `actions_last_week` too since the query already computes it.
- Build the test's mock from the presets-api handler's own response shape (or assert against a fixture captured from it) so client and server cannot drift apart again. This is the same class as [[REFACTOR-001]]: a hand-copied client contract with no shared type.
