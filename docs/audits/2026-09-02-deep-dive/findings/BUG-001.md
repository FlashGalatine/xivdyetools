# BUG-001: moderation-worker reads only the legacy language key, so it ignores every preference set through the main bot
**Severity:** MEDIUM · **Type:** State / cross-service contract drift · **Deploy unit:** `moderation-worker` · **Covered by test?** no

## Location
- `apps/moderation-worker/src/services/i18n.ts:44,79,95` — `KEY_PREFIX = 'i18n:user:'`; `resolveUserLocale` reads only that key, then falls back to the Discord client locale, then `'en'`.
- `apps/discord-worker/src/services/preferences.ts:56,59,481` — the main bot writes the unified blob `prefs:v1:{userId}` and only *reads* `i18n:user:` (migration source; nothing writes it any more).
- `apps/discord-worker/src/services/i18n.ts:105,113` — the main bot's own `resolveUserLocale` checks `prefs:v1:` **first**, then the legacy key.

## Evidence
- Both workers bind the **same production KV namespace**: `apps/discord-worker/wrangler.toml:136-137` and `apps/moderation-worker/wrangler.toml:20-21,76-77` are all id `1fcb7e037ccd4172a47fccd97cf8e753`.
- `grep -rn "prefs:v1\|i18n:user"` over both `src` trees: the only writer of `i18n:user:` is nothing — `LEGACY_I18N_PREFIX` appears at `preferences.ts:59` (definition) and `:481` (read). Language is written exclusively at `preferences.ts:680,744` under `prefs:v1:`.
- Reproduction: a user who sets language through `/preferences` on the main bot has a `prefs:v1:` entry and **no** `i18n:user:` entry. `moderation-worker/src/services/bot-i18n.ts:218` then resolves their locale to the Discord client locale or English, for every moderation-bot string. moderation-worker ships no language command of its own, so the user cannot correct it.
- Blast radius is bounded by `preferences.ts:465` ("Legacy keys are NOT deleted"): users whose preference predates the unified system still resolve correctly. It is new and re-set preferences that are lost.

## Fix
- Give `moderation-worker`'s `resolveUserLocale` the same two-step read as the main bot's (`prefs:v1:` → legacy → Discord locale → `en`).
- Better, and what [[REFACTOR-001]] proposes: move `resolveUserLocale` + `discordLocaleToLocaleCode` into `@xivdyetools/bot-logic` so one implementation serves both bots. That path needs a `bot-logic` publish before the moderation-worker deploy — two sprints.
