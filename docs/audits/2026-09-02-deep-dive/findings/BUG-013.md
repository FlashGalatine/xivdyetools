# BUG-013: moderation and submission-log embeds print dye id numbers instead of names
**Severity:** HIGH · **Type:** Logic / stainID-vs-itemID drift · **Deploy unit:** `discord-worker` · **Covered by test?** no

## Location
- `apps/discord-worker/src/index.ts:125-133` — `formatDyesForEmbed` resolves each id with `dyeService.getDyeById(dyeId)` and falls back to `dyeId.toString()` when that returns null.
- `packages/core/src/services/dye/DyeDatabase.ts:400-403` — `getDyeById` looks up `dyesByIdMap`, the **itemID** map. Its own doc at `:411` directs stain-table callers to `getByStainId` instead.

## Evidence
- Preset dye arrays carry stainIDs (1–254) after the 5.0 id rewrite, and the ranges are disjoint from itemIDs (which start at 5729 — see [[BUG-012]]'s table). So `getDyeById(1)` misses, the fallback fires, and the embed renders the raw numbers:
  ```
  Dyes: 1, 2, 3
  ```
  where a moderator expects `Snow White, Ash Grey, Goobbue Grey`.
- Affects the moderation and submission-log embeds — the surface a moderator reads when deciding whether to approve a preset, so the decision is made without seeing the palette in words.
- The test fixtures at `apps/discord-worker/src/index.test.ts:342-389` use the correct stainID shape but assert only title, components and log lines. Replacing `formatDyesForEmbed` with a bare `join(', ')` keeps the file green, which is why this shipped.

## Fix
- Resolve with `getByStainId` (or the shared `resolvePresetDye`-style helper the web app uses), keeping the numeric fallback only for genuinely unknown ids.
- Assert a rendered dye **name** in the webhook embed test, not just the surrounding structure.
- Same class as [[BUG-012]]: id-grammar call sites the 5.0 rewrite missed. The sweep is already done — of the 20 `getDyeById` call sites outside the database itself, this is the **only** one fed by preset data. The web-app callers read itemIDs out of their own persisted config and migrate on read (`dye-service-wrapper.ts:88`), and `packages/bot-logic/src/input-resolution.ts:44` discriminates explicitly with `if (n >= 5729)`. So the fix is one line, not a sweep.
