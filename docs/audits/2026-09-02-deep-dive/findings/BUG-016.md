# BUG-016: the shared web-app test mock inverts the dye id contract, manufacturing green for a whole class of defects
**Severity:** HIGH · **Type:** Untested behaviour (root cause of the id-grammar class) · **Deploy unit:** `web-app` · **Covered by test?** n/a — this *is* the test defect

## Location
- `apps/web-app/src/__tests__/mocks/services.ts:20-23` — every entry of the shared `mockDyes` is built as `{ id: 1, itemID: 5729, stainID: 1, … }`, so `id === stainID` and `id !== itemID`.
- `packages/types/src/dye/dye.ts:51-57` states the opposite contract: "`id` — always equal to `itemID` after `DyeDatabase.initialize()` normalisation … so this is an FFXIV item ID such as 5729 or 13115, **not a small sequential index**".

## Evidence
- Thirteen web-app test files import this mock, so in most of the suite `dye.id`, `dye.stainID` and "a small number" are interchangeable. In production they are disjoint ranges: stainIDs run 1–254 and itemIDs 5729–48227, with nothing in between (see [[BUG-012]]).
- Consequence: any call site that reaches for the wrong id passes its tests and fails in the browser. That is not hypothetical — it is the shared mechanism behind four separately-filed findings:

  | Finding | Site | What the mock hid |
  |---|---|---|
  | [[BUG-012]] | `result-card.ts:1189` | `dye.itemID` sent where a stainID is required |
  | [[BUG-007]] | `extractor-tool.ts:2155` | wrong-scale distance labelled as the selected method |
  | `dye-grid.ts:454` | `f`/`c` shortcuts | `dye.id` passed to handlers matching on `stainID` |
  | `budget-tool.ts:1160` | SEND TO hand-off | `dye.name` sent where a stainID is parsed |

- The reviewer that found it put it plainly: with this mock, the `f`/`c` shortcut test "cannot fail" — it asserts behaviour that only works because the fixture collapsed two different ids into one value.

## Fix
- Correct the fixture so `id === itemID` and `stainID` is the small number, matching the type's documented contract. Expect several currently-green tests to turn red — those failures are the latent bugs surfacing, and each should be fixed rather than accommodated.
- Do this **first** in any remediation sequence that touches the id-grammar findings: it converts them from "trust the audit" into "the suite proves it", and it stops the next id mix-up from shipping green.
- Consider deriving the fixture from `DyeDatabase.initialize()` output (or asserting the fixture against the real invariant in a test) so the mock cannot drift from the contract again.
