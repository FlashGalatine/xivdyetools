# BUG-011: allowlist lookups walk `Object.prototype`, so `constructor` and `__proto__` pass validation as real values
**Severity:** MEDIUM · **Type:** Edge case / input validation (one class, three deploy units) · **Deploy unit:** `@xivdyetools/core` (primary), `api-worker`, `@xivdyetools/bot-logic` · **Covered by test?** no

## Location
- `packages/core/src/types/index.ts:91-92` — `value in LEGACY_MATCHING_METHOD_MAP` then `LEGACY_MATCHING_METHOD_MAP[value]`, on a plain object literal.
- `apps/api-worker/src/lib/validation.ts:318-320` — the same pair in `parseMatchingMethod`, and it short-circuits **before** the `VALID_MATCHING_METHODS.includes` allowlist check.
- `packages/bot-logic/src/css-colors.ts:170` — `CSS_COLORS[input.toLowerCase().trim()] ?? null`; `??` cannot catch an inherited function.

## Evidence
- Runnable repro: `evidence/scripts/repro-prototype-lookup.mjs`, output in `evidence/repro-prototype-lookup.txt`:
  ```
  normalizeMatchingMethod('constructor') -> [function] function Object() { [native code] }
  normalizeMatchingMethod('__proto__')   -> [object]   [object Object]
  resolveCssColorName('constructor')     -> [function] function Object() { [native code] }
  ```
  Controls behave: `'ciede2000'` passes through and `'nonsense'` falls back to the default.
- `normalizeMatchingMethod`'s stated contract is "anything else falls back to the default", and it is the normaliser applied at every ingress — KV preference, localStorage, URL `algo`, API body. A crafted `?algo=constructor` therefore seeds a function where a `MatchingMethod` string is typed.
- Downstream, `getDistanceForMethod`'s switch has no `default:` arm, so the function falls through and returns `undefined`: api-worker answers **HTTP 200 with a null distance** rather than its normal 400, and `/contrast dye1:constructor` throws inside the handler instead of returning the localized "invalid colour" message.
- The repo already knows the fix and applied it unevenly: `apps/api-worker/src/telemetry` uses a `Map` for client-controlled key lookup and pins it with a test, and FINDING-027 added `Object.hasOwn` to `TranslationProvider.getLabel` — but its ten sibling getters still resolve through the prototype (`packages/core/src/services/localization/TranslationProvider.ts:137,170,203,236,269,…`).

## Fix
- Make the three maps `Map`s, or guard every lookup with `Object.hasOwn`. Prefer `Map` where the keys are client-controlled — it is the shape the telemetry code already proves out.
- In `parseMatchingMethod`, run the `VALID_MATCHING_METHODS` allowlist **before** the legacy-map branch so an unknown value cannot skip it.
- Sweep the remaining `TranslationProvider` getters in the same change; the class, not the instance.
- Add a test per site asserting `constructor` / `__proto__` / `toString` are rejected exactly like `nonsense`.
- Ships as a `core` publish plus a `bot-logic` publish, then the api-worker deploy — two sprints.

## Status
FIXED 2026-09-02 ef357d26 — all three lookups guarded with Object.hasOwn; api-worker runs its allowlist first.
